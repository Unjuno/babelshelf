## Connected implementation

The native product entry shares the accepted UI with a canonical IndexedDB adapter. Notes, settings, tasks, executions, notifications, folder/Trash metadata, dialogue and processing receipts persist locally. The Markdown hierarchy is a projection; explicit exports and backups create separate local files.

Natural input connects capture/search/read/answer/summary, retained dialogue/compaction and reviewed corrections. Exact generated-answer Save does not regenerate. Shared source/record checks refuse stale approvals and unapproved overwrites. Source correctness and semantic intent still have known failures; one successful generated answer is not general reliability.

Actual PC evidence exists for Bonsai4B, local Whisper tiny, Tesseract OCR, PDF text/prepared empty-page OCR and video audio transcription. Automatic Send uses only prepared readers. Original bytes, derived results and source locations are distinct. A pinned LFM2.5-VL 450M WebGPU adapter and Text + vision preset are wired for single-image description and bounded sampled-video-frame observations; standard single-image asset import/generation and offline answer/save/restart were verified on Windows Chrome on 2026-10-26 (see the dated harness acceptance report). Frame observation quality and physical-device behavior remain unverified. The Media screen now links the video-frame status directly to Vision model setup. Newly processed single-track WebM/MP4 audio has validated container offsets and estimated transcript segments; actual PC installed offline flows are recorded in VIDEO-TIMELINE.md. Legacy transcripts and edited text retain broader source coverage.

Text, Decision, Speech, OCR and Vision are independent roles. **LFM3-1.7B QAD Q4_0 is the fresh-install text default**; Bonsai 2B/4B/9B remain alternatives, and existing stored selections are not rewritten. LFM3 has a pinned model/runtime manifest, strict GGUF eligibility, a dedicated WebGPU worker/backend, explicit preparation/storage and offline-shell registration. One Windows Chrome PC product flow verified Q4 model preparation, offline cold restart, a grounded answer, exact citation and reviewed save. A separate Q8_0 product flow on 2026-10-28 verified explicit import, runtime load, offline cold restart, grounded answer and citation. A later Q8_0 run on 2026-10-31 failed to retrieve the exact saved note named in the question and produced no answer or citation; inspection found the note-ID selector was discarded. The selector fix is covered by deterministic retrieval/citation regressions and a post-fix Windows Chrome Q8 product flow: an exact named-file query returned the grounded answer, opened the original citation and saved the unchanged answer through review while browser networking was disabled. This is one PC sample, not general quality or iPhone evidence. Q8_0 is now a pinned built-in catalog/model-set choice (1.85 GB), with explicit preparation and downloads off by default; it is not silently prefetched. Q4 remains the default pending a same-task Q4/Q8 comparison of answer quality, tool correctness, load/decode, working memory and stability. Neither PC run proves selected GPU adapter use, iPhone fit, sustained performance, Stop/retry, or broad semantic quality. Liquid AI's published comparisons support prioritizing LFM3 for evaluation, but do not establish BabelShelf task quality. See [model role architecture](docs/MODEL-ROLE-ARCHITECTURE.md), [LFM3 runtime evidence](docs/LFM3-RUNTIME-SPIKE.md), and [current gates](docs/REMAINING-GATES.md). Supported custom Qwen3.5/LFM2 GGUF text models and fixed-contract D1 text-ONNX models remain available through app-owned adapters. SmolLM2 360M has separately selectable CPU/WASM Q8 and explicit WebGPU Q4F16 ONNX variants from the same pinned revision; the GPU path does not silently fall back to CPU and is not yet runtime-accepted. A bounded Whisper ONNX package was loaded and transcribed in PC Chrome with browser networking disabled, including after a page reload; the one short synthetic sample did not establish general accuracy. Arbitrary Vision architectures, arbitrary ONNX and D1-3B multimodal support remain absent. See [custom model contract](docs/CUSTOM-MODELS-CONTRACT.md).

Bundled tools execute validated code and expose SKILL.md/source identity. Versioned `Settings/harness.md` profiles choose registered read-only tools and lower-only step/result budgets. Current attachments or an opened file do not silently add unrelated Memory facts: ordinary input-scoped answers use selected original excerpts. When the user explicitly requests comparison with saved knowledge, the planner retains the profile's enabled Memory tools, retrieves exact saved sources, and answers across both validated scopes with their citations. An opened file can likewise be combined with configured Memory retrieval when requested. Enabled custom packages remain limited to their declared host callbacks. Explicitly enabled user packages pair `tools/user.<id>/SKILL.md` with `tool.js`; they are inspected as inert data, revalidated at dispatch, and run in a disposable bounded QuickJS Worker with only declared local search/read/arithmetic callbacks. Chat can request a new package and open a prefilled draft form outside attachment/file scope; local generation, review, save, and profile selection remain separate steps. When either paired source file is open, chat can propose a full-file `SKILL.md` or `tool.js` revision. The app pins the companion file, validates the pair before review and again at commit, then uses Before/After review, CAS, history and Undo. `SKILL.md` identity and capabilities stay fixed; its closed input schema can change, but that does not edit `tool.js`. Proposed code is not executed while drafting or saving. If the package was already selected in an active profile, the reviewed new revision can run on a later matching request; testing remains a separate explicit action. This is constrained local extensibility, not hostile-code-proof isolation. It does not provide external MCP transport, network/write capabilities, or general plugin compatibility. See [tool packages](docs/TOOL-PACKAGES.md) and [architecture](docs/ARCHITECTURE.md).

The harness record now also stores a finite default response style (`balanced`, `concise`, `detailed`). Settings controls and reviewed chat proposals update the same versioned record; only bounded application-owned presentation guidance enters final generation. Free-form prompts and authority changes remain outside this preference.

Settings/models.md supports up to 32 named user model sets. A set can be saved from current role selections, edited in Memory, or proposed by chat through the same review/history/Undo pipeline. Proposals can combine only already registered model IDs; they cannot add models, download assets, select a set or change execution permission.

Connection settings remain Memory-backed. Chat may propose toggling `diagnosticLogs` through review/history/Undo because entries contain only sanitized local failure metadata. Online/Offline and asset-download policy remain direct user controls and cannot be changed by a chat proposal.
