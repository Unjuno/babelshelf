## Connected implementation

The native product entry shares the accepted UI with a canonical IndexedDB adapter. Notes, settings, tasks, executions, notifications, folder/Trash metadata, dialogue and processing receipts persist locally. The Markdown hierarchy is a projection; explicit exports and backups create separate local files.

Natural input connects capture/search/read/answer/summary, retained dialogue/compaction and reviewed corrections. Exact generated-answer Save does not regenerate. Shared source/record checks refuse stale approvals and unapproved overwrites. Source correctness and semantic intent still have known failures; one successful generated answer is not general reliability.

Actual PC evidence exists for Bonsai4B, local Whisper tiny, Tesseract OCR, PDF text/prepared empty-page OCR and video audio transcription. Automatic Send uses only prepared readers. Original bytes, derived results and source locations are distinct. A pinned LFM2.5-VL 450M WebGPU adapter and Text + vision preset are wired for single-image description and bounded sampled-video-frame observations; standard single-image asset import/generation and offline answer/save/restart were verified on Windows Chrome on 2026-10-26 (see the dated harness acceptance report). Frame observation quality and physical-device behavior remain unverified. The Media screen now links the video-frame status directly to Vision model setup. Newly processed single-track WebM/MP4 audio has validated container offsets and estimated transcript segments; actual PC installed offline flows are recorded in VIDEO-TIMELINE.md. Legacy transcripts and edited text retain broader source coverage.

Text, Decision, Speech, OCR and Vision are independent roles. Bonsai4B remains the default. Supported custom Qwen3.5/LFM2 GGUF text models and fixed-contract D1 text-ONNX models can be added through app-owned adapters. SmolLM2 360M now has separately selectable CPU/WASM Q8 and explicit WebGPU Q4F16 ONNX variants from the same pinned model revision; the GPU path does not silently fall back to CPU. The exact WebGPU model has not yet been loaded or generated in a real browser/device, so this registration is not runtime acceptance. Both ONNX manifests identify the actual locked Transformers.js 4.3.0 / ONNX Runtime Web 1.31.0-dev pair. A bounded eight-file Whisper ONNX package was loaded and transcribed in PC Chrome with browser networking disabled, including after a page reload. The one short synthetic sample produced text whose accuracy was not established. Custom OCR adapters, arbitrary Vision architectures, arbitrary GGUF/ONNX and D1-3B multimodal support remain absent. Registered custom LFM2-VL packages have a bounded local import and preparation adapter; their actual model/device execution acceptance remains open. Extensions alone do not prove compatibility. See [custom model contract](docs/CUSTOM-MODELS-CONTRACT.md).

Bundled tools execute validated code and expose SKILL.md/source identity. Versioned `Settings/harness.md` profiles choose registered read-only tools and lower-only step/result budgets. With current attachments or an opened file, the coordinator exposes only `math.calculate` when enabled by the active profile; global Memory and custom tools remain unavailable, while grounded answers cite only the selected original input/file. Explicitly enabled user packages pair `tools/user.<id>/SKILL.md` with `tool.js`; they are inspected as inert data, revalidated at dispatch, and run in a disposable bounded QuickJS Worker with only declared local search/read/arithmetic callbacks. Chat can request a new package and open a prefilled draft form outside attachment/file scope; local generation, review, save, and profile selection remain separate steps. When either paired source file is open, chat can propose a full-file `SKILL.md` or `tool.js` revision. The app pins the companion file, validates the pair before review and again at commit, then uses Before/After review, CAS, history and Undo. `SKILL.md` identity and capabilities stay fixed; its closed input schema can change, but that does not edit `tool.js`. Proposed code is not executed while drafting or saving. If the package was already selected in an active profile, the reviewed new revision can run on a later matching request; testing remains a separate explicit action. This is constrained local extensibility, not hostile-code-proof isolation. It does not provide external MCP transport, network/write capabilities, or general plugin compatibility. See [tool packages](docs/TOOL-PACKAGES.md) and [architecture](docs/ARCHITECTURE.md).

The harness record now also stores a finite default response style (`balanced`, `concise`, `detailed`). Settings controls and reviewed chat proposals update the same versioned record; only bounded application-owned presentation guidance enters final generation. Free-form prompts and authority changes remain outside this preference.

Settings/models.md supports up to 32 named user model sets. A set can be saved from current role selections, edited in Memory, or proposed by chat through the same review/history/Undo pipeline. Proposals can combine only already registered model IDs; they cannot add models, download assets, select a set or change execution permission.

Connection settings remain Memory-backed. Chat may propose toggling `diagnosticLogs` through review/history/Undo because entries contain only sanitized local failure metadata. Online/Offline and asset-download policy remain direct user controls and cannot be changed by a chat proposal.
