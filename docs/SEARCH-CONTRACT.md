# Local lexical retrieval

Canonical notes and revisions remain the source of truth. `dist/core.js` builds an in-memory derived index from current eligible originals/generated records. Withdrawal, stale-derived sources and missing media originals keep their existing eligibility rules. Reindexing or searching never rewrites bodies, IDs, paths or history.

Unit48 uses NFKC/lowercase query normalization. Latin words and Unicode decimal numbers are complete lexical tokens; hyphen/underscore compounds stay together. Query tokens containing a decimal digit, hyphen or underscore must occur completely in the candidate excerpt or title/aliases. Other keywords retain OR ranking, not semantic or all-word matching. A wrong code cannot be replaced by a partial code. Punctuation alone is not evidence. Non-Latin letters/marks retain character grams and single-character lookup. This is bounded lexical retrieval, not language understanding, stemming or universal relevance.

Search excerpts retain UTF-16 start/end into the exact original body. At normal700-unit chunk boundaries, complete lexical spans of up to700units extend adjacent excerpts rather than becoming partial-word evidence. Overlap is possible. Expansion is bounded to2098units; callers still enforce their real token budgets. A single lexical span longer than700units is omitted where it crosses chunks, while surrounding text remains searchable. This bound is a retrieval limitation, not truncation/mutation of stored originals. It does not establish large-archive/mobile resource acceptance.

Tests cover code prefix/suffix confusion, width/case normalization, word versus incidental bigram matches, CJK single-character lookup, Hindi/Arabic marks, Unicode decimal codes, aliases and exact long-document source ranges. Native PC offline-context evidence is in TEST-RESULTS.txt Unit48. No model, network fallback, persistent schema migration or execution authority is introduced.

## Agent search across local and web sources

The user-facing operation should remain one natural-language search request. Internally, keep the local and Web adapters distinct so the app can explain where results came from and apply different evidence rules. `memory.search` is the always-available Offline path: it searches the device's current local Memory index. It is not a general Web search and must not be described as one. Importing or saving a Web result is a separate user-visible action; search alone never changes canonical Memory.

In Online mode, one search request may combine local Memory results with a distinct `web.search` adapter backed by a user-configured RustXNG service. RustXNG is the preferred first adapter because its HTTP API can return ranked result metadata and optionally page text for grounding, while its MCP stdio interface is not directly callable by a browser PWA. Keep the adapter boundary protocol-based so a compatible SearXNG JSON endpoint can be added without changing the agent contract. The Web adapter runs only when the app's explicit connection mode is Online, the browser reports a usable connection, and an endpoint is configured. When any condition is false, local search still runs and the result clearly says that Web results are unavailable; it never silently sends the query elsewhere. A Web timeout or service error must not discard successful local results.

RustXNG is a separate service, not a browser library or an iOS API. A user may run it on a PC/server and connect while reachable, or run it on the same machine as a desktop browser. A phone's `localhost` is the phone itself; reaching a PC-hosted service requires a reachable address and browser-compatible HTTPS/CORS configuration. Do not silently install a server, publish it to the internet, or make a public RustXNG instance the default. The service may forward queries to selected upstream search providers even when the RustXNG process itself is on a private LAN; disclose that behavior and respect each provider's terms.

RustXNG's optional local BM25 index is experimental, disabled by default, and requires a separately managed crawl/index. It is not a substitute for the app's always-available local Memory index or imported snapshots. Do not claim offline Web coverage merely because RustXNG can hold a local index; its documented local-index mode merges with upstream search and does not provide its own offline-only answer mode. If an already-running local RustXNG service is available offline, its indexed results may be offered as an explicitly separate, bounded local-web source, while the app's local Memory path remains independent.

Do not hard-code a public RustXNG or SearXNG instance. RustXNG's HTTP API may be self-hosted, but actual browser reachability depends on endpoint address, TLS and CORS; its documented MCP stdio service is for a local agent process and cannot be called directly from the PWA. Prefer a same-origin app-owned gateway or a user-configured, HTTPS, browser-compatible endpoint. Validate the configured origin and bounded JSON result fields; accept page text only from a URL returned by the same search session. Treat titles, snippets and page content as untrusted data. Preserve exact URL, canonical URL when available, retrieval timestamp and service/session identity as external-source metadata; revalidate page identity and exact ranges before citing claims. Web snippets alone are discovery hints, not citable evidence. Citations must remain visibly distinct from local Memory references. Do not persist search queries or external content unless the user explicitly saves them.

The app now exposes `web.search` as an optional built-in tool backed by the separately tested RustXNG HTTP client. It is offered to the agent only when Online is selected, a user endpoint is configured and the browser reports a connection; invocation checks the browser signal again and uses cancellation. The query is sent only to that configured service. Search results are bounded and validated; successful raw page text may be given transiently to the agent, while snippets are marked discovery-only. Durable activity receipts retain query and content byte counts, result counts, and extraction status, never the query, snippets, URLs or page text. Saving an endpoint does not install RustXNG or make any request. Web citation rendering, mixed-source final-answer binding and reviewed save of Web originals are still not implemented; until then, the app must not present RustXNG results as verified UI citations or save them to Memory. Local search remains available in either connection mode. RustXNG adoption is a protocol integration decision; it does not require bundling its server or adopting its AGPL-3.0-or-later code into BabelShelf.

### External evidence boundary milestone

`design/prototype/src/web-evidence.ts` remains an isolated evidence boundary: bounded, session-scoped RustXNG page snapshots and citations bind exact UTF-16 ranges to host-owned snapshot text. Model-selected source labels can resolve only to labels the host offered; a model cannot mint a URL, retrieval timestamp, quote, or offset. The mixed-label binder can route one host-offered label catalog to either a structurally verified Memory ref or a Web citation checked against the live snapshot; the caller must still run the existing canonical Memory validator before presenting Memory refs. The RustXNG HTTP client requests optional page text, accepts it only with `raw_content_status: ok`, and bounds each returned page body to 12 KB at a valid UTF-8 boundary before citation processing. It preserves RustXNG's `raw_content_truncated` signal and marks client-side truncation; neither case is described as a complete page. Failed, blocked, missing, or unknown extraction statuses are never citable; result snippets remain discovery hints. The new agent adapter is Online-gated and receipts do not persist raw web data, but it is not yet wired to this evidence binder or citation UI. Local Memory citations and their validation path remain unchanged. The next integration step is to keep snapshots in turn memory, bind final answers to separate Web citations, render them separately and persist external content only through an explicit reviewed save action. A future reviewed save transaction must validate staged Web originals and generated Memory refs together; current `applyKnowledgeChanges` validates generated sources against preexisting records only, so a direct batch insertion would fail its source checks.
