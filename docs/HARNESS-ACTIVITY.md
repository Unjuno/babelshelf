# Interactive harness activity

Activity is local audit data on each canonical dialogue turn (`ui-v1-dialogue`). It is not a second knowledge store, a tool registration or execution authority. Older turns without activity remain readable; no records are cleared or retrospectively fabricated.

The interactive adapter records allowlisted read-only stages: model load, bounded context/compaction, action selection, note search/read, original dialogue read, literal text operations, correction proposal and answer generation. Existing approved correction writes retain their separate atomic correction receipts; scheduled runs retain their canonical execution ledger. PDF and speech extraction use the separate processing ledger below; asset preparation is not yet recorded there.

Each attempt stores schema1, a stable ID, operation name, exact bounded JSON input, start timestamp and status. The start commits with expected-dialogue CAS **before** the operation begins. Completion stores a detached result or a typed error and finish timestamp. Terminal entries cannot be completed twice or switched to another input/tool. Tool-returned failures retain both their result receipt and failure status. A failed start prevents execution; a failed final write never repeats the operation or asserts a tool failure after actual success.

A process interruption may leave `running` persisted. Outside that exact active input it is displayed as `Incomplete`: this does not claim the work failed, completed or never ran. There is no automatic replay. Stop retains a stopped attempt when the underlying operation returns/cancels; this does not promise instantaneous cancellation of GPU loading/compilation. Failure to persist a terminal record is shown explicitly and may leave an incomplete entry.

Activity payloads are portable JSON, limited to300,000 UTF-8 bytes each, nesting depth20,128 entries per turn. Invalid operation/status/time/result shapes, duplicate IDs, nonfinite values and cycles reject. Codes distinguish stopped, changed source, context limit, unprepared model, malformed model output, unavailable target and other failures. Messages remain local; error classification is a UI/audit category rather than proof of cause.

Normal conversation shows one small activity mark. The sheet opens short operation/state labels; details expose input/result/error on demand. Activity is explicitly excluded from dialogue history/compaction projection, search evidence and instruction parsing. Backups preserve and validate it as untrusted receipts. A rehashed backup does not convert an unknown operation into a valid one. User data and receipts are never uploaded by this flow.

A note read resolves from the same refreshed snapshot that hydrates its display. Navigation uses its resolved path. This prevents an activity saying a new version was read while an older in-memory list paints a different file/version. This is snapshot consistency, not a claim that another tab can never make a later edit.

Verification scope: pure lifecycle/control tests and real IndexedDB reopen/CAS/brainpack tests are separate from actual browser/model outcomes. Exact builds and observed failures are in TEST-RESULTS.txt. Incomplete activity, older status-only failures and unrelated historical source marks are preserved; this feature does not retroactively repair semantic answers or establish mobile/offline acceptance.


## Media processing history

Explicit PDF reading and audio/video-audio transcription persist schema1 `media-processing` receipts in existing `runs`, keyed `ui-v1-processing-ID`. Each wraps the same bounded Activity lifecycle with allowlisted `pdf.read` / `speech.transcribe`. The start commits before original preparation, decoding or extraction. A failed start prevents work. Terminal CAS accepts only the original running identity once, preserving input/tool/time; concurrent completion cannot overwrite a terminal. Cancellation checks surround asynchronous work and normalize an aborted decoder/worker rejection to Stopped. A terminal persistence failure never replays work or falsely asserts an engine failure. Interrupted running receipts display Incomplete outside the active attempt; no automatic replay.

Settings > Local files > Processing history opens receipts on demand. Rows show source label and Done/Failed/Stopped/Incomplete. Details reveal timestamp, bounded JSON input, result summary or error. Refresh and dismissal use the existing preview epoch: stale history reads cannot reopen or replace a newer sheet; an old cancelled PDF audit error may toast but cannot close another sheet. History queries use an IDB key-prefix cursor so original byte records are not copied into the list.

Inputs retain a fresh-file descriptor or stored original reference and display name, plus explicit speech language/selected model. File labels are untrusted display data, never evidence. Success retains original ID/hash, processor or actual speech-model revision/runtime, character count and `textStateHash` (the canonical stateHash of the exact returned string), page coverage or audio scope/duration/segment count. The result is a compact processing receipt; it does not duplicate the full extracted body or media bytes. `reviewRequired:true` means the returned extraction requires the existing review flow. Done proves processing completed, not that a note was saved, a transcript was accurate, or every media region was understood. Closing review retains the attempt but does not save extraction/original knowledge. Existing explicit Save/Use text/Send contracts remain unchanged.

Receipts from unsent files can therefore refer to an original that was never saved. They do not require an original-asset record and cannot be used as search evidence, context, a canonical transcript, write authority or permission to retry. Backup validates reserved prefix/type/ID/tool and lifecycle even after rehashing; exact records survive full-state restore. Older data is not retroactively fabricated or rewritten. There is no automatic pruning or replay; the existing 200MB/20,000-entry backup limits still apply. Very large history pagination/retention remains a separate usability requirement.

PC verification includes actual PDF.js extraction before/after audit writes, seven real-IDB lifecycle/restore checks, native multilingual PDF completion, password failure, actual Whisper video-audio recognition and Stop, reload, and exact backup/restore. Lifecycle-only concurrency/interruption fixtures are explicitly distinguished from inference. Physical microphone/device/background delivery/full offline-process acceptance and asset-preparation attempt integration remain unverified or pending; see TEST-RESULTS.txt.
