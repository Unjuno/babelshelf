# Local state backup

The accepted product exports `.brainpack` schema2 from one readonly IndexedDB transaction over the existing schema1 `notes`, `settings` and `runs` stores. The database version and existing records are unchanged. It includes every canonical note/revision/source/withdrawal, settings Markdown, original dialogue and compaction cursor, empty-folder/recovery metadata, correction receipts and newly persisted attachment originals. Registered schedules, execution history and notifications are canonical notes and travel together. Unknown JSON metadata is retained; no record is removed to export or restore.

The envelope has `format: mobile-local-brainpack`, a SHA-256 checksum and a payload with schema, createdAt, notes, settings and runs. Settings/runs are arrays of `{key,value}` so their out-of-line IDB keys survive. The payload includes `undefinedPaths`: paths into notes/settings/runs whose JSON null placeholders decode to present properties containing undefined. This preserves optional legacy fields and distinguishes missing/null/undefined during conflict checks. Paths must exist as own properties; decoding never follows inherited properties. Unsupported structured-clone values such as Date, Blob or typed arrays fail export rather than being silently discarded. This format is for the current persisted data; a future asset format must explicitly handle binary originals.

SHA-256 covers the encoded envelope payload through the same deterministic JSON/optional-value encoding used for whole-state fingerprints. It detects accidental file changes, not malicious authorship. All imported content remains untrusted data. Parsing validates canonical identities, paths, historical source ranges, known preference/task documents, dialogue and correction-operation references. Historical references can point to a withdrawn original's retained revision; withdrawal still prevents its reuse as current model evidence.

Restore preview shows counts and conflicting paths/keys. A full-state restore refuses every write if any existing same-ID note or same-key auxiliary value differs. Identical entries skip. Current-path/source errors also refuse restoration. The preview pins a whole-state fingerprint; another tab changing any store before approval invalidates the review. Save uses a single readwrite transaction over all three stores and never overwrites an existing record/key. A failed transaction cannot leave half a conversation or a receipt without its note. Newly imported schedules retain exact prompt/history/cursor but require explicit review before execution. Newly imported downloads-ON connection documents append an OFF revision, retaining the imported original; restoring a file cannot authorize downloads. Models/runtime readiness are verified independently from actual local assets.

Folder/Trash hydration is read-only. Explicit user changes serialize compare-and-swap writes against their last committed values. Hydration and recovered display batches cannot overwrite a newer tab. Export and restore drain these local queues before snapshot/review/commit. After a metadata conflict the user must reopen to read current state before further changes.

Legacy schema1 note-only files remain readable. They contain no auxiliary state. A schema1 file containing new asset-linked notes is refused because it lacks the required original bytes; use the product state backup instead. The low-level legacy restore retains its earlier non-overwriting note merge; the accepted UI reports conflicts before enabling Restore. Both formats apply the same new-schedule/download safety guards. Export still uses schema2; the preserved `dist/` baseline's own export/parser remains schema1.

Original asset records use bounded base64 JSON and have independent ID/revision/size/SHA-256 checks, required canonical projections and dialogue links. They are not arbitrary Blob values bypassing the codec. Parsed originals must match immutable v1 projections/provenance even if the outer checksum was recomputed. Export uses compact JSON and checks its UTF-8 byte size against the same200MB input limit. A larger state fails export explicitly; partitioned/streaming backup remains an open large-collection requirement.

Excluded explicitly: model assets, inference runtime assets, unsaved drafts and unsent or older unpersisted attachment originals. Legacy descriptors without original bytes cannot recover those bytes. A conflicting initialized destination (including different built-in/settings records) is not silently replaced or merged. Divergent same-ID histories and conversation reconciliation need a separate review flow; users must keep the source backup. No complete fresh-device restore UI or storage reclamation is claimed.

Working speech descriptors in dialogue include the reviewed transcript and optional exact recognized-text range in the user prompt. These are validated against the included raw originals, model/language/estimated ranges and exact prompt bytes. They do not require a derived searchable transcript note; original raw projections remain empty until actual explicit creation/correction. A backup can retain an edited voice prompt without falsely claiming it matches the recognized words. Historical source withdrawal remains portable, but a new submitted turn cannot reuse a withdrawn original.

Interactive dialogue activity is retained in the same settings record and schema2 snapshot. Lifecycle/JSON/operation validation applies to imports; receipts remain untrusted local audit data and never schedule or execute an operation. A pending attempt remains incomplete after restore, with no automatic replay. Historical raw failure messages and results are preserved. See HARNESS-ACTIVITY.md.

Explicit model asset operations also travel as untrusted processing receipts in runs, with manifest pins and historical outcomes. The model/runtime bytes remain excluded. Restoring a successful Prepare/Load receipt never installs, enables, downloads or loads a model; current readiness is separately inspected from real local assets. Missing terminal records remain incomplete and are never replayed. See HARNESS-ACTIVITY.md.


Long restore reviews use the same scrollable fields and fixed action row as schedule/media reviews. Conflict paths can scroll independently while Cancel and the disabled Restore remain visible. This changes layout only: any conflict still refuses all writes, and whole-state approval fingerprint checks remain authoritative. ## Explicit Restore new (Unit41)

Strict restore remains the default and refuses all writes on any conflict. For schema2 only, review may offer Restore new when at least one new entry exists and retaining every current conflicting ID/key yields a valid combined graph. This explicitly keeps all existing canonical values and adds only absent records/keys; it does not reconcile skipped versions or restore their conversation/settings. The source backup must be retained for skipped contents. Review shows conflict labels and new record/linked-entry counts. Unresolvable dependencies disable restoration.

New-only commit requires a reviewed whole-state fingerprint, recomputes the plan inside the same three-store readwrite transaction and uses add-only writes. It retains task quarantine/download-OFF guards. It refuses new correction receipts or Trash recovery snapshots targeting conflicting notes, new executions targeting conflicting tasks, and runs matching an existing task's retained pending cursor. Every new execution history revision must match its actual retained task revision's prompt/definition and valid source ranges. Whole merged graph validation then applies. These conservative refusals avoid indirectly rewriting retained data through Undo/Trash or blocking a retained schedule. Existing strict/legacy behavior remains unchanged; arbitrary history reconciliation and fresh-device full-state recovery remain separate unfinished work.

## UTF-8 allocation reduction (Unit88)
The existing schema2/checksum/200MB contract remains. Byte-size admission now counts UTF-8 bytes directly from UTF-16 code units, including paired and lone surrogate behavior identical to TextEncoder, rather than allocating a full encoded copy for a length check. Canonical SHA-256 feeds UTF-8 in chunks of at most65536 UTF-16 code units, keeping a valid surrogate pair together. Digests remain byte-for-byte compatible with prior backups and state/CAS hashes. No new archive version or migration is needed.

This removes complete UTF8 byte-buffer allocations at these two stages. Whole-state snapshots, undefined-value encoding, JSON strings, Blob download and restore parsing still allocate; no measured peak-memory or arbitrary-size streaming claim follows. Partitioned archives, >200MB collections, quota pressure and mobile memory acceptance remain open. No data/cache/history cleanup accompanies export.

## Reviewed ordinary-note recovery (Unit91)
A conflicting existing active original note in Inbox/Notes can be reviewed individually from Restore backup using Review <current path>, Before/After, then Restore as revision. A new destination revision receives only the selected backup latest body; current ID/path/metadata and every destination revision remain. The full backup note/version branch is separately retained in a note-restore receipt and visible under Backup history. No source path is adopted and no old branch is deleted. Restoration never runs a prompt, model, task or downloaded code.

This action is limited to ordinary original notes with no sources or original/derived-media links; generated/source-bearing notes, withdrawn records, system/protected/settings/tools/schedule/notification records are not routed through this body-only recovery. Their existing add-only/settings/specialized flows remain. Same-body/different-history-only archive import, arbitrary metadata/source-graph changes and conversation reconciliation remain incomplete. This is not a universal divergent-history merge.

Preview pins the full notes/settings/runs fingerprint. Approval reparses the untrusted backup and checks the full current fingerprint inside one readwrite transaction before appending the revision and receipt. Any intervening store change aborts both writes and requires a new review. The receipt pins source ID, original backup checksum, before/after destination versions and the archived complete source branch; import/export validates its relationship to the retained after revision. Later local revisions/withdrawal do not remove that archive. Checksums establish integrity, not source authorship. No implicit model/library/connection/readiness or restore replay authority crosses this path.
