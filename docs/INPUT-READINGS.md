# Attachments in Input

The accepted Input UI supports a question with local image/PDF/audio/video-audio text without first saving a separate note manually. This extends the existing TXT/Markdown import behavior. It does not add sessions or a second conversation UI.

## Review and storage

Read text runs the real prepared local processor. Use text retains the existing draft and other attachments and stages the exact reviewed metadata under the raw attachment ID. It writes no canonical note. Remove discards that pending item; reload before Send does not preserve pending work. Save note remains an explicit alternative.

Send is a durable import action: one transaction checks the expected dialogue revision, original identities, extraction metadata and current original state, then writes new raw originals, separate OCR/PDF/transcript text notes and the input turn. Existing originals are reused without copying bytes. Duplicate extraction IDs, conflicts, malformed reading links and withdrawn targets abort the entire transaction. A failed transaction keeps the draft/attachments available. Stopping subsequent inference leaves the successfully imported originals/text and a stopped input turn; it does not silently undo the import.

A dialogue attachment's reading field contains kind, canonical extraction note ID and first revision only. Exact text, processor pins, pages/regions and original hashes remain on the extraction record. Full-state backups retain both; validation rejects cross-file, mismatched kind/version, orphan or forged original links. Historical links remain valid after later correction/withdrawal; those historical references never restore current evidence eligibility.

## Grounding and intent

Current readable attachments include TXT/MD originals and OCR/PDF/transcript derivatives. Retrieval is scoped to those files, with one leading relevant excerpt per file before extra matches. Raw binary-note bodies provide only dependency eligibility and cannot enter the derived-file evidence. All current files must contribute an excerpt within the actual tokenizer budget; failure asks for fewer attachments. Results describe selected excerpts rather than whole-file comprehension. Partial PDF coverage remains recorded and shown in review/pending status.

Bounded dialogue history may clarify what the user means or the requested format, but supplies no additional attachment facts. Old note pins are excluded from this current-input scope. Inputs are revalidated before and after generation; changed/withdrawn evidence fails, including uncited selected files. Exact canonical references let source marks open the correct original image regions or PDF pages.

Natural requests still reach the existing planner. For already reviewed current inputs, a model read/search/chat choice continues through scoped retrieval to an answer rather than stopping at a global search list. Explicit literal search/open commands retain navigation behavior; capture/edit/recall/transform/summary keep their separate paths. This policy follows an actual native failure where a factual attachment question stopped at Found results. Capture requests for a new note use grounded generation from the selected files, discard planner-authored factual content, and present exact generated text/source refs in New file review. Save writes that content without another generation. An explicit selected past user/assistant message retains its original text and citations instead of being replaced by current attachments. Existing-note edits keep their separate Before/After approval; the source-only semantic correction adapter has not gained arbitrary cross-file factual rewriting in this unit.

## Automatic prepared readers on Send

Ordinary Send now attempts PNG/JPEG OCR, PDF text-layer extraction and audio/video-audio transcription before the atomic import. OCR and speech use only the selected, already prepared local models; missing assets never trigger a download. PDF processing uses bundled local PDF.js assets. Original bytes remain separate and immutable. Successful automatic derivatives are labelled extracted, not reviewed. Their first text revision and processor provenance remain available for direct correction/history and exact original-source previews. Manual Read/Use text/Save note remains available when inspection before Send is preferred.

An unavailable/unsupported/empty/failed reader leaves that attachment unread, preserving its original and per-item error with the submitted input. If any requested media remains unread, factual question answering is refused rather than inferred from filenames or old dialogue. Successfully extracted attachments may still be saved in that same import. PDF pages with no text layer now run prepared-only local OCR; see PDF-CONTRACT.md for schema2 page pins, raster limits and fallback boundaries. Without prepared OCR, empty PDF text reports OCR required. PDF text is bounded to the existing page/text limits, image processing supplies recognized text only, and video supplies audio only: the evidence explicitly excludes unprocessed scenes/frames and unmapped container timing.

Stop before import aborts the owned OCR/PDF worker or speech request, discards transient extraction results and retains the draft/attachments; completed processing receipts remain audit history. Audio decode/render cannot be interrupted mid-browser-call, so cancellation is checked immediately after each and its result is discarded. Stop after an import keeps committed originals/extractions/dialogue. Ledger write failure aborts Send rather than silently degrading to an unread result. Editing a draft while extraction is running preserves the newer text when the submitted snapshot commits. Pending drafts remain session-only until Send.

Speech extraction uses the same strict reading-link shape and canonical transcript metadata as other readers. Source previews preserve estimated audio ranges and whole-original video playback; no frame understanding or precise video seeking is claimed. No decision-model runtime, provider fallback or permission expansion is added.

## Unread-question recovery (Unit102)
When current attachments cannot be read and factual answering/summary is refused after their originals were committed, the original question and submitted attachment references return to an empty composer through the same guarded recovery used for inference errors/Stop. They reuse canonical original IDs and any committed reading refs, not fresh File objects or duplicate original writes. A newer draft/attachment selection is never overwritten. Original saved status stays on the earlier turn; it does not claim that the question was answered.

The user may prepare/select a compatible local reader, then explicitly Send again. Recovery does not prepare/download models, run readers or automatically replay a question. Empty-text original imports and explicit search/read actions retain their existing behavior. Unsupported formats remain unsupported; retry does not invent extraction. The staged composer is still session-only, while already submitted originals and earlier turn are durable.

## Execution query authority (Unit162)
Current-input answer/summary/new-note generation takes its retrieval query from the literal current human request, not the planner's history-derived search hint. Current files are already selected by canonical ID/revision. groundingQuery is shared by the UI dispatch/activity input and the grounded reader boundary, so alternate callers cannot reintroduce old attachment facts through retrievalQuery. The raw planner output remains in dialogue.plan unchanged; knowledge.answer records the actual execution query. Knowledge/file/history requests without current readings retain their existing query handling. History still supplies bounded request/format context, not extra attachment evidence. This does not repair invalid labels/quotes, relax source validation, force an answer, authorize writes or establish general semantic accuracy.

## Prepared image understanding in ordinary Send (2026-10-20)

The existing selected Vision role now participates in the same automatic-reading and atomic input-submission pipeline. For supported PNG/JPEG images, an explicitly selected Vision model owns image reading; it must already be prepared. The adapter receives the literal current question (or a short visible-content request when no text was supplied). It has no download or knowledge-write authority. An unprepared, unsupported or failing selected Vision model does not silently become OCR. With no Vision selection, the existing prepared OCR path remains available; explicit Read text and PDF OCR are unchanged.

Vision results are generated observations, not extracted verbatim text or verified facts. A reading link uses kind vision and points to its own canonical v1 record with exact original ID/revision/hash, question, dimensions and model/runtime pins. Current-input evidence states that these observations may be incorrect or speculative and cover one image only. Existing source validation and revalidation stay mandatory. A citation proves the stored observation's source chain, not that the image model's claim is true. The original remains inspectable on demand.

Send stores raw originals, separate observation records and the dialogue attachment links in the existing single transaction. Backups validate the new typed links and preserve prior OCR/PDF/transcript links. Stop terminates the vision worker, rejects pending work and refuses late output before commit. A committed import remains durable if a later text-answer attempt fails or is stopped; no automatic retry or inference is added. Manual Ask about image continues to offer reviewed Save without regeneration.

A single self-contained question explicitly naming current attachments may now take a finite read-only answer route before model action selection. It retains the literal query and current-file IDs/revisions, without unrelated dialogue context. Commands, multi-question/compound requests, earlier-dialogue references and ambiguous subjects still use the planner/approval routes. This avoids making a small model select an operation when both the read-only intent and supplied subject are already explicit; it does not repair or accept invalid planner output.
