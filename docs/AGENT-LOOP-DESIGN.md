# BabelShelf agent loop

Updated 2026-10-31. This describes the local, sessionless turn loop; it does not copy a desktop agent runtime into the PWA.

## Current tool coverage gap

The six registered read-only agent tools are `memory.search`, `memory.list`, `memory.read`, `memory.sources`, `math.calculate`, and `time.now`; reviewed write operations use separate final application actions. `memory.sources` inspects provenance/status for explicitly selected records; it does not return source text or replace an exact read. `time.now` returns a single device-clock instant, local time, offset and available zone as a typed tool result. It is in new Standard profiles; existing profile selections are preserved. Users can change built-in tools for the active profile in Settings → More → Assistant; changes are saved as revisions of `Settings/harness.md`. Tool observations are distinct from saved-source citations. Device clock errors and changing time zones remain limitations; a clock reading does not imply reliable background scheduling or notification delivery. Controlled tests exercise planner, receipt and answer paths; real-model selection and time interpretation remain unverified. Custom tool packages can compose their currently declared local capabilities; the clock and source-status inspection are not automatically granted to custom code. `mcp.example` is an inert template, not a connected external MCP server.

**MCP boundary:** agent calls currently pass through the MCP SDK's in-memory client/server bridge for one turn (`mcp-agent-bridge.ts` → `mcp-local-adapter.ts`). It only exposes the host's already-registered `read` + `network: 'none'` tools, with schema validation, cancellation, and an 8,000-character JSON result bound. This is an internal protocol adapter, not a remote MCP connection. There is no Streamable HTTP external-server transport, external network tool, or server-process launch in the PWA.

## What to borrow

- **Hermes Agent:** a central tool registry and dispatcher, typed tool errors returned to the model, execution progress, and an explicit loop that feeds tool results back into the next model call. Its broad turn budget and server/provider failover are not suitable defaults for a phone-first offline app.
- **Pi agent:** distinct lifecycle events for model turns and tool execution, schema validation before execution, cancellation, and sequential execution when operations depend on each other. These make a long-running operation observable and stoppable without making the UI itself own orchestration.
- **OpenClaw:** a finalization pass after tools settle, so a successful tool batch does not accidentally become the user's final answer. Its gateway/session infrastructure is not needed by this PWA.
- **Vercel AI SDK:** explicit per-step control (`prepareStep`) and composable stop conditions. This supports changing the available tool set as evidence arrives, but BabelShelf should retain its own model/runtime adapters rather than adopt the SDK's remote-provider assumptions.
- **OpenAI Agents SDK:** a small set of primitives around an agent runner, function tools, validation/guardrails and continuation; its documentation also distinguishes managed agent loops from owning the loop directly. This is useful for keeping orchestration small and tool checks at the execution boundary. Cloud tracing, provider integration, and agent handoffs are optional patterns, not BabelShelf requirements.
- **LangGraph:** explicit state transitions plus checkpointed pause/resume at interrupt points. This is a useful reference for resumable workflows that must wait for user review, but a graph runtime for every chat turn would add machinery to this sessionless PWA.
- **Hugging Face smolagents:** a clear model action → tool observation → next model step loop. The ReAct pattern is useful for conceptual clarity; its Python runtime and code-agent execution model are not a direct fit for this browser app.
- **LFM3's own training and tool contract:** the LFM3-1.7B model card says it was post-trained for agentic harnesses including Hermes Agent, Pi and OpenClaw. Liquid's current tool-use guide documents the expected cycle (tool schema → assistant call → tool-role result → next model response), plus deferred tools: keep their schemas in the request's full tool catalog, reveal discovered definitions as `tool_reference` content parts in the tool result, and pass the full catalog again on subsequent generations. This is direct compatibility guidance for LFM3, not a reason to copy any one harness wholesale. The same model card cautions that 1.7B is not recommended for complex multi-step reasoning, so retrieval and deterministic tools must supply missing knowledge and the product must still verify real task completion.

These are design references, not dependencies. See [LFM3 model card](https://huggingface.co/LiquidAI/LFM3-1.7B), [Liquid's tool-use and deferred-loading contract](https://docs.liquid.ai/lfm/key-concepts/tool-use), [Hermes loop](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/developer-guide/agent-loop.md), [Pi agent core](https://github.com/badlogic/pi-mono/blob/main/packages/agent/README.md), [OpenClaw loop](https://github.com/openclaw/openclaw/blob/main/docs/concepts/agent-loop.md), [Vercel AI SDK loop control](https://ai-sdk.dev/docs/agents/loop-control), [OpenAI Agents SDK runner](https://openai.github.io/openai-agents-python/running_agents/), [LangGraph state/interrupt model](https://docs.langchain.com/oss/javascript/langgraph/thinking-in-langgraph), and [smolagents implementation](https://github.com/huggingface/smolagents/blob/main/src/smolagents/agents.py).

### Cross-harness principles that apply here

1. **A model proposes a call; the runtime validates and executes it.** Do not let prompt text or model output expand the registered tool catalog.
2. **Every result returns to the model as data.** Preserve typed success/failure, source identity and bounded content; failed calls are not evidence.
3. **The loop has explicit continuation and finish semantics.** A completed read is not itself the user-facing answer when the request asks for one.
4. **Cancellation, budgets and recovery are runtime behavior.** They must work independently of a particular model's formatting or reasoning quality.
5. **Pause/resume belongs at real interaction boundaries.** Use it for a user review or a resumable operation, not as a general graph for ordinary chat.

These principles align with BabelShelf's current design: a model-directed sequential loop on top of a stable app-owned registry, with canonical Memory data and revisions outside the prompt. The current implementation does not add a framework dependency or delegate work to remote services.

### Inference residency and turn latency

The same prepared Text model remains resident across turns while its model/runtime/context identity is unchanged. `TextEngineRouter.load()` returns a reuse result for that exact resident identity; `createLfmTextRuntime.load()` also avoids rereading the OPFS file or unloading the active session when the same LFM model is already loaded. The model execution manager does not evict a warm Text model just to run the optional Decision classifier, and native-tool Text planners own action selection themselves. A real role switch (for example, a prepared Decision model followed by Text inference, or a vision/speech reader) releases the prior idle role before loading the next one because the app currently permits one inference role at a time in an origin. That trades reload latency on role switches for a lower simultaneous memory footprint. Returning to a model after such a switch, a changed model/runtime identity, worker recovery, or a cold app restart can reload weights; none of those cases should be described as same-model per-turn reloads.

The default LFM3 route is WebGPU-first. The worker requests a high-performance adapter and all model layers, but those requests are not proof of adapter identity or GPU allocation. CPU WASM fallback is allowed only for an explicitly unavailable WebGPU API/adapter; initialization, integrity and allocation failures remain errors. Runtime offload logs provide bounded placement evidence.

The pinned LFM3 worker now requests exact-prefix reuse after a completed call. The wrapper forwards native recurrent checkpoint controls, with full-SWA storage retaining the attention positions needed by checkpoint restoration; arbitrary KV shifting remains disabled. Stop, errors and unload invalidate reuse. Model residency and prompt-state reuse are distinct. The actual PC cached/fresh comparison and memory tradeoff are documented in LFM3-RUNTIME-SPIKE.md; phone fit and sustained quality remain unverified. Native tool catalogs and the initial request stay stable across ordinary loop steps; changing budget/error feedback is appended after call/result history so it does not rewrite the reusable system prefix. This does not force native reuse when a tool catalog, request or retained context changes.

Native function calling and legacy JSON action routing now use separate system-instruction builders in the same planner. The native path describes the request, registered functions, accepted guide discovery, observed evidence and reviewed completion. It does not also inject legacy target/dispatch instructions. Both paths still use the same host validators, source binding, cancellation and reviewed-write contracts; shortening instructions does not relax those checks. Dynamic execution feedback stays after the native call/result history. This reduces conflicting transport instructions, but actual model selection and answer quality must still pass the dated browser task flows.

Tool discovery, guide reads and folder listings are typed descriptive observations, distinct from custom execution results and original knowledge excerpts. The existing evidence module validates them through the shared projector and exposes `toolInfo` to native/legacy answer dispatch. This lets the agent answer a guide/listing question without a Memory search or package invocation. A guide never proves package execution; a filename never proves its contents. Its accepted native result and callable schema represent the state once, without a duplicate not-yet-executed reminder.

When the current user request names an exact enabled custom ID, the coordinator prepares that guide through the existing audited reader before the model's first decision. Unknown IDs, disabled tools, paths and substrings do not match. This is explicit metadata selection, not task classification or package execution; it respects the same result and activity budgets. The model then decides whether to invoke the package or finish from the guide. Discovery by capability remains available when no ID is known. No new agent layer, automatic package activation or write is introduced.

### Gap found by comparing harness patterns with the implementation

The reference list above is useful only when it leads to an explicit implementation decision. A source review on 2026-10-29 found a material gap: the exported loop is `runReadOnlyAgentLoop`, and its capability contract used to encode effect as a boolean `readOnly: true`. This obscured the distinction between a local read, a review proposal, and a network operation. The registry now carries a finite effect/network pair; the current loop intentionally accepts only `read` + `none`, and custom packages still expose only `memory.search`, `memory.list`, `memory.read` and `math.calculate`. The in-memory MCP bridge is a protocol adapter around this registry, not a source of new capabilities. The model therefore cannot mistake an app-owned create/edit final action for a committed function call.

That separation is now explicit in code: the loop protocol consumes a registered capability's typed effect/network pair, while `runReadOnlyAgentLoop` admits only local reads. Registration and schema validation precede dispatch; the host records execution, observes cancellation, and returns typed outcomes. A review or external effect is still rejected before planning because the corresponding continuing-loop adapters have not shipped. Adding one must not grant a package direct host or IndexedDB access.

Apply this distinction to concrete operations:

- Local search, list, read and deterministic calculation can run directly and return evidence.
- Explicit model-free new-note capture is add-only and writes the exact submitted body to Inbox. A body authored by the model is a generated proposal and opens the existing review before persistence; source lineage is retained where available. Copying an already-generated assistant answer remains reviewed, and existing-file edits stay revision-checked and reviewed.
- An edit can produce an expected-ID/expected-version proposal. The existing history, conflict check and explicit approval remain authoritative; a model call must not turn into an overwrite or deletion.
- An external MCP operation is a separate, opt-in capability. It is unavailable in Offline mode and must report what data leaves the device before it is enabled. A browser-side MCP client cannot launch arbitrary stdio servers.

This reconciles the useful harness patterns without copying a desktop agent's shell access: Hermes/Pi-style registry and execution events, the model-action/observation loop used by ReAct agents, OpenClaw-style loop recovery and post-tool finalization, and LFM3's native call/result protocol all fit above the same effect-aware app registry. LangGraph-like checkpointing belongs only at an actual review or resumable operation boundary. The effect-aware registry and final-action review handoff are implemented; review-effect loop tools and remote MCP transport are not.

### Implementation sequence and acceptance evidence

Phase 1 has a narrow code implementation: tool capability records use `effect: 'read' | 'review' | 'external'` with `network: 'none' | 'explicit-online'`; the registry validates legal pairings, bundled/custom tool packages declare read effects, and the read-only loop rejects review/external effects before planning. Agent calls use a local in-memory MCP client/server bridge around those same host-validated operations. This does not add review-effect tools, a remote Streamable HTTP MCP client, or external network capability.

1. **Effect-aware registry.** The finite effect declaration is in place. Keep the active profile as the source of available IDs; model text, SKILL.md and tool results must never register a capability or change its effect. Continue to prove an unknown ID, effect mismatch or malformed schema never reaches execution.
2. **Unify tool calls with existing application actions without duplicating them.** Add-only explicit capture and reviewed correction already exist as final application actions. Keep exact content, source lineage, unique path selection, version conflict and review contracts; make the handoff observable through the same turn coordinator. Add a continuing-loop proposal tool only if a real multi-step task needs it and it can reuse the existing storage/review transaction. Tests must prove capture never overwrites, stale edits conflict, approval appends history, and saving generated answer text does not regenerate it.

   **Current implementation clarification (verified 2026-10-31):** this handoff exists at the planner's final-action boundary; capture and edit are deliberately not registered as looping tools. `planDialogueAgent()` accepts a final `capture` or `edit` action after useful read-only tool calls. Explicit model-free literal capture (including `Remember:`) writes the exact submitted body to a new Inbox record and selects a numbered sibling on name collision. A planner/Decision-authored body is marked generated and opens the existing new-note review before any save; saving an existing assistant answer also stays in that reviewed sheet. Edit binds to an exact discovered/opened note revision and opens the existing correction review. The originating `DialogueTurn` records the saved path or correction review outcome. Do not add duplicate `memory.capture` / `memory.edit` tools or a second receipt store merely to resemble another harness. Add a continuing review-effect tool only if a concrete workflow requires model continuation after a proposal; if that happens, reuse this existing turn ID and review/CAS path.
3. **Progressive skill/tool discovery.** Keep the small core tool catalog visible and reveal custom SKILL.md and schemas only after local discovery. Use the native deferred-tool mechanism when the selected model/runtime supports it; keep an equivalent discover/read/use sequence for JSON planners. Tests must show that undiscovered tools cannot execute and deferred schemas do not leak into the initial prompt.
4. **External tools last and opt-in (not implemented).** Add a remote MCP-compatible browser transport only after local contracts work. Offline mode must exclude external tools before planning; Online mode alone must not silently connect or transmit personal data. The user must explicitly configure and enable an endpoint, and each tool's data boundary must be visible. Test with a local mock transport and assert zero network access in Offline mode. Existing MCP calls are in-memory and remain within the local registry.

   **External MCP transport baseline (checked 2026-10-29):** target Streamable HTTP, not stdio, because a browser PWA cannot spawn arbitrary server processes. The current MCP revision is `2026-07-28`: each request carries protocol version/client metadata, HTTP mirrors required metadata into headers, each call is a POST, and response streaming is request-scoped; the revision removed implicit protocol sessions and the GET event stream. Earlier `2025-11-25` and older servers still use the initialize/session era. A client that claims broad compatibility must detect the era from a protocol response and fall back only on the specified legacy signal; CORS refusal, authentication failure, timeout, or offline failure must remain visible errors, not trigger a speculative alternate request. Keep discovery, pagination, schema validation, server/tool identity namespacing, result-size bounds, cancellation, and untrusted tool descriptions/results in the adapter contract. The MCP tool UX must show enabled tools and invocation activity and let the user deny a call; it need not add a confirmation dialog for every already-enabled read. Any operation with external side effects or payloads containing private Memory excerpts needs a clearly disclosed, user-controlled boundary. These are requirements for a future remote transport; the current in-memory adapter does not implement them. See the versioned [Streamable HTTP specification](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http), [versioning and compatibility](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning), and [tool protocol](https://modelcontextprotocol.io/specification/2026-07-28/server/tools).
5. **Model/harness evaluation.** Run the same saved-knowledge tasks against each supported planner protocol, including multi-document retrieval, create-and-review, correction conflict, cancellation, context pressure, stop-after-tool finalization, and no-progress recovery. Record real-model results separately from fake-runtime contract tests; do not call a tool-selection path verified from schema tests alone.

Do not begin phase 4 by embedding a desktop agent framework, and do not call phase 1 complete merely because a new `effect` field compiles. Each phase needs executable behavior and boundary tests before the next capability is exposed.

## BabelShelf turn contract

```text
user input + selected local context
  -> choose a registered app tool or a response action
  -> validate the exact tool ID and arguments against its schema
  -> execute through the app-owned tool registry
  -> record a bounded receipt and source lineage
  -> feed the result back as untrusted data
  -> repeat while the task needs work and the user has not stopped it
  -> return final content with source labels, then validate/display/review
     (legacy protocols use a separate grounded generation), or report a typed failure
```

The model chooses among tools made available by the active harness. The harness owns tool registration, argument validation, local execution, cancellation, provenance, context limits and state persistence. This preserves model autonomy over *which task operation to perform* while keeping data and execution behavior deterministic. Search, folder listing, read and calculation do not require per-call confirmation. `memory.list` returns only immediate children with stable note IDs and versions; it is a projection of IndexedDB-backed notes and folder metadata, not a filesystem. A listing is navigation metadata, not evidence for an answer. Knowledge changes continue through the existing revision and review contract; no model gets a raw IndexedDB or host-filesystem escape hatch.

The turn loop is sequential by default because a later operation often depends on an earlier result. Parallelism may be added only for independent, read-only calls with stable result ordering. “Read-only” describes the tool's persistent-data effect; it does not prove that host execution is free of turn-local state. The coordinator updates the set of exact searchable IDs/paths and the latest search results while tools run, and custom-tool provenance is accumulated in the same turn. A batch may run concurrently only after those per-turn updates are isolated per call and merged deterministically; otherwise retain model order. A tool error is a typed result with no evidence; it must not look like a successful answer. When a search finds a candidate, exact IDs or paths returned by that result are the only basis for a subsequent read. For the explicit search → read → answer request, if the model passes the quoted passage instead of a selector and the latest search has exactly one unique record, the coordinator binds the read to that record's canonical ID. Multiple hits remain ambiguous and are never auto-selected. Large results are bounded before they re-enter context. Stop/cancel and context exhaustion terminate the loop with the completed receipts preserved. If the model immediately proposes the exact same tool and arguments after a typed failure, execution stops instead of repeating a known failure; a changed call remains available to the model. This is a no-progress guard, not a general call ceiling.

### Loop recovery adapted from other harnesses

A `batch_not_executed` entry is a placeholder for an unrun call, not a failed execution. The model may select that remaining work on its next step. Immediate-repeat detection looks through trailing skipped placeholders, so they neither block a useful unrun call nor hide the preceding no-progress signal for the guarded call. The original batch entries remain in history to preserve call/result pairing.

OpenClaw documents several distinct loop protections: an always-on repeated-identical-error stop, optional rolling pattern detection, and a post-compaction repeated-outcome guard; a first critical intervention gives the model one recovery response and a repeated intervention ends the run. BabelShelf uses a smaller local variant in `agent-loop.ts`: within the last 16 attempts it detects a third occurrence of the same tool, arguments and bounded result, and returns `no_progress_loop` to the model. Different searches may legitimately return the same empty result and are allowed to continue. This means varied-wording loops can run until another limit, cancellation or a model decision stops them; the activity and context budgets remain in force. A repeated identical call after the recovery signal stops under the immediate-repeat guard. When this guard interrupts a batch, remaining calls are recorded as `batch_not_executed` without running them, preserving paired tool history. See [OpenClaw's loop-detection contract](https://docs.openclaw.ai/tools/loop-detection) for richer configurable behavior.

OpenClaw's compaction implementation preserves assistant tool calls with their matching results when choosing a split point. BabelShelf currently handles **planner tool-history pressure** differently: when the selected model's context is full, it progressively omits older result payloads from a planner-only copy, marks them as omitted, and keeps every call and its result entry in place. Native tool-call/result IDs therefore remain paired. The loop's canonical attempts and source receipts remain unchanged and are still used to construct answer evidence and citations. If the planner still cannot fit after omitting prior payloads, the loop returns the existing evidence-grounded partial-work path. This is not semantic summarization, does not compact the saved conversation transcript, and does not claim that omitted content remains available to the planner. A future transcript compactor may summarize dialogue, but summaries cannot replace source evidence; source IDs, revisions and ranges must remain lossless.

There is no arbitrary built-in small call count. An optional user harness profile may set a finite tool-call budget. The 128-event limit is only the inline `turn.activity` limit: because the production store supports paged receipts, further events are persisted in IndexedDB pages. Therefore the production paged route does **not** derive a total tool-call budget from 128 and does not claim that total receipt history is unlimited; storage quota or persistence errors can still stop the operation. `activityBoundedToolBudget` and its reserve are a compatibility bound for a route without paged persistence. That fallback estimates four receipts per tool attempt (planning start/finish and tool start/finish), and reserves four receipts for the terminal plan/answer plus six for the three distinct bounded planner repairs. This is a conservative storage bound, not a product work limit. Normal runtime boundaries are cancellation, model context/output capacity, the optional profile limit, bounded tool results, schema/source validation and repeated no-progress detection. Context fitting and the per-generation output ceiling are not a per-turn compute budget. If the legacy answer-generation input cannot leave its minimum output reserve after all validated operation results are included, none of those results are silently removed: the turn fails before generation with an actionable context message, while the already-recorded operation receipts remain available. This differs from planner-loop exhaustion, where the app can make a clearly partial answer from retained evidence. Activity detail now derives an observed rollup from successful `dialogue.plan` planner receipts, successful `knowledge.answer` generation receipts, and finished registered-tool receipt intervals. Final-answer receipts retain available numeric inference measurements and non-content metadata, not answer text, citation text or source IDs; public dialogue results do not expose the diagnostic counters. The display omits unavailable counters and remains diagnostic usage visibility, not a stop condition or a global compute budget. It does not estimate device memory/energy or count paths that finish without generation. Controlled tests verify both measured-answer aggregation and answer-content omission; live-model behavior under long varied tool sequences and actual quota failure remain unverified.

After a failed tool call, an immediate identical proposal is withheld and returned once as `no_progress_loop`, giving the model one opportunity to change strategy; repeating it after that signal terminates the turn. Planner history compaction only reduces what is sent back to the model; it never edits canonical attempts, source receipts, dialogue, or notes.

A native response mixing a final action with any other call is rejected before all tool execution. Its bounded diagnostic lists only registered function names, not arguments. The single native repair uses the host-defined mixed-final reason to explain that reads must return before a final response; neither diagnostic payload nor untrusted model prose becomes an instruction. A second protocol failure ends the turn. This is more precise feedback, not a higher retry budget.

### Final content without duplicate composition

For native function models, successful Memory tool rows carry host-assigned source labels. The model chooses each continuation, including after search; legacy automatic-read/synthesis shortcuts do not replace a requested skill workflow. After any tool attempt, the offered terminal functions and the final validator share `AGENT_RESULT_ACTIONS`: answer, summary, new-note/copy capture and reviewed edit. Initial UI navigation, dialogue transforms and schedule/tool creation are not advertised as terminal steps that the existing agent boundary would reject. Registered read tools remain available. This fixes a contract mismatch, not a new restriction on useful tool sequences or an increased retry budget.

Initial native navigation uses `finish_open_file` and `finish_show_search_results`, bound to the existing read/search screen actions. The functions end the request to display one file or matching files; `memory.read` and `memory.search` return evidence for continued work. This naming and purpose boundary replaces ambiguous `finish_read`/`finish_search` after actual Q4 and Q8 models selected two terminal reads as if they were ordinary batch reads. It does not change UI structure, storage or legacy JSON action IDs. Reject unoffered or mixed terminal calls as before.

The model completes answer/summary/new-text capture with a reply object in the existing final function. The application rebinds and validates sources against current originals, then displays the same answer or opens existing review; it does not regenerate that draft. Legacy protocols and current attachments retain their grounded-answer path. Answer language follows the explicit language request or latest user message; English tool guides must not switch it or introduce guessed translations of names. This uses existing evidence, receipts and review/CAS storage. See CONVERSATION-CONTRACT.md for the boundary and TEST-RESULTS.txt for controlled versus actual model evidence.

### Warm model lifetime

The model used for a Send is acquired through the app-wide inference owner and `TextEngineRouter`; it is not intentionally loaded once per tool step or once per Send. When a healthy worker already holds the same model, model revision, runtime revision and context profile, `load()` returns a reuse result and the loaded session remains available for the next inference. A change to that identity, an explicit unload, worker failure/recovery, registry replacement, or arbitration in favor of another inference role can evict it. Automatic acquisition is prepared-only: it verifies local runtime assets and does not silently download missing files. This avoids redundant warm loads while still preventing a stale session from crossing model/runtime changes.

When a selected text model exposes native tool calls, the text model now owns first-pass action/tool selection; the separate Decision model does not run ahead of it on each ordinary message. This follows the LFM3 training protocol and avoids the otherwise repeated Decision → Text role switch, which unloads one resident model before acquiring the other. Models on the JSON planner path retain the optional Decision-first route. This is a residency and latency policy, not a claim that native tool calls improve reasoning quality; the local app registry still validates and executes every call.

This is an app-lifetime guarantee while the owner and worker remain alive, not a promise that iOS keeps a Web Worker or GPU allocations resident across Home Screen suspension, OS memory pressure, browser termination, or an app update. Node contract tests verify reuse and the documented eviction paths; they do not measure model load time, GPU memory, or mobile suspension. A device diagnostic should report a later cold reload as a new load, not as proof that every Send reloads the model.

## Model protocol boundary

LFM3's published model card says the model was post-trained for harnesses such as Hermes Agent, Pi and OpenClaw. Its chat template accepts tool schemas and documents the assistant-call → host execution → tool-result round trip. This means the checkpoint is trained to emit and consume familiar tool protocols; it does **not** include those harnesses' registries, tool implementations, retries, cancellation, persistence or safety behavior. The model card also cautions that LFM3-1.7B is not recommended for complex multi-step reasoning. The host therefore owns turn state, evidence, recovery and stop conditions while the model chooses operations. Liquid AI's separate harness guide shows those frameworks connecting to a locally served OpenAI-compatible endpoint; that deployment shape is not a reason to add a server to BabelShelf's browser-only offline path. See the [LFM3 model card](https://huggingface.co/LiquidAI/LFM3-1.7B#tool-calling) and [Liquid AI's local agent-harness guide](https://docs.liquid.ai/examples/agent-harnesses).

### Native reasoning and transient context

For native LFM3 tool calls, exact counting and generation both use `enable_thinking:true` and `preserve_thinking:false`. Non-native LFM3 operations retain their non-thinking setting. The current native tool turn carries bounded assistant content, including streamed reasoning, in its matching assistant `tool_calls` message; the template drops older reasoning. This is transient planner context, not a user-visible answer, a new persisted activity field, or a source of write authority. Final normalization accepts only the validated final function arguments. Existing receipts and knowledge are not erased.

This change follows a reproduced guide-only failure with reasoning disabled and a focused real-Q8 completion with reasoning enabled; it is not a claim that reasoning always improves a small model. Duplicate guide-completion/execution reminders were also removed: the accepted tool result and revealed schema represent guide state once. Keep exact count/template parity, Stop, context/output limits, and actual grounded-task checks as acceptance criteria. Reasoning adds decode time, so report it within total output and latency rather than comparing only visible words. Detailed successes and failures remain in [TEST-RESULTS.txt](TEST-RESULTS.txt).

### Output budget follows the selected engine

The app carries each selected runtime's `maxOutputTokens` through the shared inference identity and router manifest. LFM3's adapter ceiling is 3,072 tokens; LFM2 and Qwen retain their registered ceilings up to 768. Native agent generation reserves the selected output allowance within the exactly counted remaining context, since that operation includes reasoning, tool syntax, and any final answer. A concise visible-answer preference does not reduce the entire native operation to 256 tokens. The legacy JSON planner and separate prose-answer path retain their own style-based budgets. Contract tests verify selected-engine ceilings and remaining-context bounds; they do not establish model quality or device memory fit.

### LFM3 sampling defaults

The official LFM3 model card recommends `temperature=0.1`, `top_k=50`, and repetition penalty `1.1` for general chat, tool use and agents. The pinned Wllama adapter now applies those request-level values only to LFM3; LFM2/Qwen retain their existing deterministic temperature setting. This aligns the app's defaults with the model owner's published recommendation without changing the model, runtime, prompt protocol or user data. The adapter contract tests prove that Wllama receives the values; they do not prove sampling semantics, better task success, lower repetition, or improved answer quality on the real checkpoint. Keep a paired live-model comparison as a performance/quality gate when adequate memory is available. See the [official LFM3 model card](https://huggingface.co/LiquidAI/LFM3-1.7B#inference).

BabelShelf keeps constrained JSON as the protocol for engines that support it. LFM3 advertises a separate native-tool protocol: the planner passes registered function schemas through exact token counting and generation, accepts streamed native tool-call deltas, then normalizes one call or a bounded independent read-only batch into the existing validated dialogue-plan format. The app registry and coordinator still own execution, receipts and the next model step. Do not infer real-model compatibility from the contract tests alone. The protocol adapter boundary is:

```text
model-specific prompt / tool schema / parser
  -> canonical Plan (registered tool ID + typed args | final action)
  -> existing agent loop and coordinator
```

The product adapter parses bounded streamed tool-call deltas and rejects malformed JSON arguments, non-object arguments and incompatible constrained-JSON mode. There is no separate fixed eight-call batch ceiling. The planner is told the remaining configured profile budget when one exists. Paged receipt persistence means there is no activity-derived total tool-call ceiling on the production route; a non-paged compatibility route may use the inline activity reserve. With no configured per-turn call ceiling, prompt instructions do not invent a numeric limit. The active built-in tools and custom tools whose local guides have been read remain available at each planning step; the model chooses whether to search, list, read, calculate, use an enabled custom tool or finish. The host validates each call against the registered schema and current exact-source ledger, then executes calls sequentially. It does not infer that calls are safe to run concurrently. This is a deliberate current constraint: the coordinator maintains turn-scoped state such as exact-read targets, latest search IDs, deferred-tool visibility and custom-tool evidence. Parallel calls could race those ledgers or make a later `memory.read` selector ambiguous. A dependent batch member can be rejected at the execution boundary if its exact ID was not supplied by the user or returned by an earlier tool. The model may continue with another plan or finish honestly. Planner history reconstructs a batch as one assistant `tool_calls` message followed by a result message for each call ID. The LFM3 stream parser, model-result adapter and history validator share a 128-call transport bound; this is a per-generation protocol/resource bound, not a per-turn compute budget. Controlled protocol tests cover schema parity for count/generation, configured-budget instructions, batch validation, sequential execution and grouped history replay. Cumulative token/compute-time accounting and long varied-sequence behavior remain open. A future parallel executor should first move those ledgers to per-call immutable results and prove independence, then preserve the model's call order in recorded history; copying another harness's concurrent executor alone would not be safe here.

Tool-selection steps keep a bounded protocol budget. Native source-backed finish_answer, finish_summary and finish_capturetext use the answer policy from reply-style.ts instead of the old planner ceiling. These functions share one required reply={status,answer,sources} shape before and after retrieval. The source argument is now limited to the exact currently visible labels (empty-only when none exist), rather than a constant S1..S64 pattern. An actual correct operation answer invented S1 under that broader schema and was rejected. Source-set changes can invalidate prefix reuse; correctness takes precedence and the runtime still performs exact counting. Failed or unchanged evidence does not change the catalog. Schema hints do not replace host validation or prove model compliance. A second source-free completion function is not offered: an actual model chose that escape path and omitted citations. New original notes before tool execution can use an empty source list; empty/failed retrieval cannot become an asserted saved fact. Exact labels bind only observed eligible original ranges. The final answer is validated and displayed/reviewed once, with no second paraphrasing generation. Native and separate grounded generation share the same comparison guidance: claims must follow observed evidence; source differences do not establish unstated chronology, cause, proximity or suitability. Exact source validation is not a general entailment test. A real answer with valid citations still added an unsupported nearer-location claim; its draft was discarded and remains a quality failure in the evidence. Legacy JSON and attachment routes retain their separate grounded-generation path. Detail is bounded by the selected context and manifest, never a phone-specific hidden short-answer cap.

The LFM3-native adapter is integrated at the product boundary. Actual PC runs have completed search, exact read, source-bound comparison and reviewed save; earlier protocol and semantic failures are retained in TEST-RESULTS.txt. Use the recorded build for each observation. Neither mock protocol tests nor a successful small comparison establishes general answer quality, custom-tool completion, physical phone fit or offline cold-start acceptance.

### Progressive tool discovery across planner protocols

The current LFM3 model card documents more than native function calls: deferred tool definitions can stay out of the prompt until a search tool returns `tool_reference` parts, after which the chat template inserts the referenced schemas. It says to keep the complete tool catalog available to the template on each request. This is directly relevant if BabelShelf grows beyond the small active tool set: passing every skill's full schema on every planning step needlessly spends context and makes tool selection noisier. The card also says LFM3 was post-trained for Hermes Agent, Pi and OpenClaw; this indicates protocol familiarity, not that it inherits those harnesses' runtime, safety, or task-completion guarantees. See the [official LFM3 tool-calling and tool-search description](https://huggingface.co/LiquidAI/LFM3-1.7B#tool-calling).


Both native and JSON planners use the same local discovery contract: show built-in schemas, tools.search, tools.read-skill, and the names of enabled custom tools initially, then expose a custom execution schema after its exact local guide has been read successfully in this turn. A known enabled ID is directly readable; search is optional navigation, not another authorization gate. Failed or oversized guides cannot expose callable schemas, and inactive or unregistered IDs remain unavailable. The pinned Wllama exact-count API accepts string content, and its llama.cpp transport does not preserve defer_loading or tool_reference through to the template. Template-level support alone therefore does not establish runtime compatibility. The app sends ordinary native assistant/tool messages with JSON-string results and concrete registered schemas; unsupported deferred transport fields are rejected before inference. Discovery never supplies executable schemas or capabilities.

When context fitting omits a verbose discovery result or guide, retain only exact registered IDs in transient history. Its content is marked omitted; the model may reread needed guidance. The original history remains intact, and schema availability is not accidentally revoked. A full configured catalog retains both discovery functions: the configuration limit remains 64, while the planner permits those two application-owned entries in addition. The shared native transport bound includes scoped final functions without increasing the execution budget.

### Operation results and original citations

The answer contract distinguishes original knowledge excerpts from successful operation results. Calculations, device-clock readings and enabled custom-package results can support an answer without a saved-note citation. Discovery and guide reading alone cannot. The native planner accepts a source-free terminal answer only after an actual registered, successful result remains visible in its current prompt; failed, omitted or unregistered results do not qualify. Context fitting recomputes that eligibility. If original source labels are present, their existing citation checks still apply.

Native citation labels follow first successful observation order across both built-in and custom tools. A later built-in search cannot move its results ahead of earlier custom-host originals and rebind their labels. Context fitting keeps the initial label catalog for identity, but offers only still-visible evidence in the final schema: omitting S1 does not rename S2 to S1. This changes transient prompt labels only; canonical IDs, revisions, ranges and exact quotes remain unchanged. The corresponding regression reproduces a custom read of two originals followed by a search returning a derived comparison.

`agent-evidence.ts` snapshots bounded custom JSON once for the same turn. The coordinator, native planner and separate grounded-answer route consume that shared projection. Custom result fields cannot mint source IDs or revisions; actual Memory reads keep the separate host-observed provenance path. The result is operation data, not an independently verified saved fact. Native completion displays the validated answer without a second generation, while the legacy answer route includes those transient results explicitly. Durable activity continues to store package identity and payload sizes rather than raw custom arguments/results. This adds no permission, storage schema, network route or alternate loop.

The coordinator also retains bounded original observations by the loop's exact attempt index. It publishes them only after custom execution, result projection, activity persistence and cancellation checks succeed. The native planner wraps that successful custom result as `{result, originals}` and assigns labels only to the host-observed originals. Package-authored fields stay inside `result`; they cannot define trusted sources. Failed/skipped/unregistered attempts and results omitted during context fitting contribute neither original payloads nor labels. Context fitting changes only the prompt projection, preserving canonical observations for the existing final freshness check. The generic loop supplies an attempt index but owns no knowledge-store or source policy. Real QuickJS regression covers a failed read followed by a successful read and a source-bound native completion; the model in that contract test is controlled, so arbitrary custom retrieval quality still needs actual-model acceptance.

The native completion bridge can normalize nonempty zero-call assistant text into a read-only answer with empty source references. It never interprets that text as an action. Existing planner validation accepts this path only with visible successful operation evidence and no required original-file citations or attachment scope; truncated, empty, failed or omitted results still cannot finish. The pinned PreparedGgufAdapter currently uses `tool_choice: 'required'` for both counting and generation: the prompt therefore instructs the model to use the offered final functions. Zero-call normalization is contract-tested tolerance, not a live-model acceptance result or an advertised alternative on this runtime. If a single final function has a conversational preface, only its function arguments are validated and used; the preface is discarded. Mixed final/read calls remain invalid. This normalization is confined to the native runtime bridge and uses the existing answer contract rather than adding a parallel loop or transport protocol.

Native catalogs omit the legacy terminal calculator: arithmetic is a registered `math.calculate` operation, followed by the same answer completion used for other operations. The explicit expression shortcut and legacy JSON adapter retain their existing path. This avoids offering a terminal action that cannot consume prior tool results; no extra retry loop is introduced. Native prompts likewise omit the legacy calculate(action/query), blanket no-prose and mandatory-query instructions. Function schemas describe native arguments; JSON-only output rules remain with the JSON adapter. Protocol separation prevents the prompt from contradicting the runtime completion contract.

Native answer/summary completion requires the complete `reply`, without a redundant required search query. An omitted query normalizes to an empty string only after terminal reply validation; malformed supplied queries still fail. `finish_answer` returns a result without creating a file. `finish_capturetext` proposes a new note only when the current request asks for one; earlier saved work in dialogue is not a current save request. Both paths retain the same evidence validation. This boundary was clarified after a real count-only task returned the correct result but unnecessarily opened New file review. The unrequested draft was discarded, and the failed intent decision is retained in the test evidence.

### Dialogue headroom before tool execution

Initial preparation now checks room for tool observations and the requested answer, not only whether one minimal plan fits. The preferred reserve uses the existing planner allowance and response-length policy. For a large current request or fixed catalog, it is capped by half the remaining space after the exact request/protocol count; the minimum protocol output must still fit. This is a compaction trigger for archived dialogue, not a smaller device-specific context window or a new output cap. Compaction preserves every original turn, latest result identity, source references and save conflicts. Live tool results still use their bounded per-step projection, and unbounded tasks can still exhaust context. This does not guarantee every registered result or long document fits.

Controlled tests cover metadata search, exact ID/schema fidelity, string-only count/generate messages, guide-before-call enforcement, full-catalog discovery, context omission, result projection and rejection of unsupported deferred fields. Tool guides remain transient; receipts retain bounded metadata. Actual-model custom-tool selection and execution still need a targeted end-to-end acceptance case. The host registry, not the returned description, supplies the executable schema and capabilities.

When adapting ideas from other harnesses, retain only their useful runtime contracts: registry dispatch and typed tool outcomes (Hermes), lifecycle/cancellation and pre-execution schema checks (Pi), and an explicit post-tool answer/finalization step (OpenClaw). Their gateway, session, server and host-shell features do not belong in this browser PWA. This is a protocol/loop boundary decision; it does not narrow the model's choice among tools that the active app profile registers.

## What this changes now

The agent loop does not infer a mandatory search → read sequence from an ordinary request. It exposes the same active local tool set throughout the turn and lets the model decide whether a search excerpt is sufficient, a full read is needed, multiple sources should be compared, or it should stop. The legacy JSON planner retains one narrow deterministic completion for an explicit search + read + answer request: after a successful search with exactly one unique record and a complete, non-omitted read of that record, the host selects the already-requested grounded answer phase without spending another planner inference. It does not apply if more tool work follows the read, the task crosses source scopes, search is ambiguous, or the read is partial. In that legacy path, successful projected results for explicitly named files accumulate within the turn; once every named file resolves unambiguously, the host batch-reads exact IDs through the normal registry. Native planners receive the results and choose their own next tool or supported final action, without these implicit read/synthesis shortcuts. This works when the model searches files separately and for Japanese filename-first requests. It does not declare the task complete when a named file is missing or ambiguous; subsequent comparison, calculation, or recovery remains model-planned. Instructions otherwise recommend search for topics and exact reads for full source ranges, but these are guidance rather than application-enforced stages. The host remains strict about execution facts: an invented `memory.read` selector is rejected before storage access; only successful results become evidence; an answer that claims to have read a source without a successful read is disallowed by the prompt and citation pipeline; incomplete work must be reported honestly. User requests that explicitly require a read can be checked as acceptance criteria without baking that sequence into every turn. Selector recovery is retained only for a unique record from the latest successful search and never guesses among multiple matches.

The planner keeps model choice and host invariants separate. Tool selection, order and stopping remain model decisions; registration, schemas, exact selectors, cancellation, work budgets, provenance, no-progress detection, and review boundaries remain host decisions. See `agent-loop.ts`, `dialogue-agent.ts`, `agent-coordinator.ts`, `conversation.ts`, `harness-actions.ts`, and `structured-grammar.ts`.

## Current capability gap

The registered tool-call catalog is narrower than the app's full operation set. The registry describes tools with a finite `effect` (`read`, `review`, or `external`) and a matching network declaration. The current agent executor deliberately accepts only `read` + `network: 'none'`; `buildActiveToolRegistry` activates the six built-in IDs listed above or paired `user.*` packages, and custom packages are adapted to that read-only effect with Memory search/resolve and calculation capabilities. No review-effect or external tool is active in the registry. Native models can request supported final `capture` or `edit` actions through the separate final-action contract; they cannot commit a write or call a remote MCP server as a registered loop tool. Explicit capture adds a new Inbox note without overwriting, while edits and copying an existing assistant answer use review. This is intentionally distinct from a direct knowledge patch tool.

This boundary must be addressed before describing custom packages as freely extensible. A future package contract should declare capabilities per tool (for example, local read, reversible Memory write, local calculation, or optional network access), and the host should enforce the declared capability. Normal reversible app-local work should not require repeated permission dialogs; revisions and an Undo/trash path preserve recovery. External network access remains user-controlled by the existing Online/Offline setting. A tool's `SKILL.md` is guidance for selecting and using it, while its code, typed schema and declared effects define executable behavior. The registry must never treat Markdown instructions as executable code or let a model-authored description grant new capabilities. Do not add duplicate `memory.capture` or `memory.patch` tools just to make the function list look uniform; extend that list only when a distinct, validated tool operation needs to continue the agent loop.

Review-effect tools that continue the loop and an optional remote MCP connector are real extensibility gaps; create/edit proposal flows already work as final actions. Local tool calls are carried over the internal in-memory MCP bridge and remain bound to the app registry. Hermes/Pi/OpenClaw are useful for the model/tool/result loop and lifecycle semantics; their server gateways, shell access, background sessions and broad provider failover do not establish that those capabilities fit an offline-first PWA. Add only concrete local packages or adapters that complete a user task, then test their full round trip through the same model-independent loop.

These references should guide distinct parts of the design rather than dictate a framework choice: Hermes and smolagents for model → tool → observation cycles; Pi for cancellation and typed lifecycle; OpenClaw for no-progress detection and finalization; LangGraph for a persisted pause/resume at an actual review boundary; MCP for interoperable tool discovery and request/result envelopes. None of those patterns implies that the browser-local implementation needs a server, shell access, provider failover, or a graph for each turn.

### Tool effects and review boundary

Keep the two existing model-selected operation forms distinct, but under the same turn coordinator:

| Form | Examples | Model may do | Host must do |
| --- | --- | --- | --- |
| Registered tool call | `memory.search`, `memory.read`, `math.calculate`, enabled `user.*` | Call directly and use bounded results for the next planning step | Validate exact schema and registration, execute locally, record typed outcome and provenance |
| Final application action | `capture`, `edit`, `schedule`, `tool-create` | Request one validated operation or proposal after any needed tool steps | Capture adds a new record; edits, schedules and tool drafts use their existing review surfaces |

The actual code implements both forms: `DialoguePlan` carries tool calls and final application actions; native-tool engines receive registered functions plus `plan_action`; capture/edit flow through `submission-workflow.ts` and existing before/after or new-note review. Both routes are recorded on the same turn. `SubmissionOutcome` distinguishes `awaitingApproval`, while the originating `DialogueTurn` records the review or save status; tests cover generated-note review, answer copy without regeneration, and exact sourced correction. There is no need for a second user-visible activity history or receipt store. Tool calls continue the planning loop, while capture/edit are final application actions handed to review. Therefore do **not** add duplicate executable `memory.capture`/`memory.patch` packages merely to imitate another harness's function list. The remaining gap is a review-effect tool only if a concrete workflow needs model continuation after the proposal; any such adapter should reuse the existing turn ID and review/CAS path.

Executable custom code remains limited to the `read` effect and local declared capabilities; the new effect union is not a permission grant. The read-only loop rejects `review` and `external` tools before planning or execution until their dedicated adapters exist. A Memory proposal must carry exact target ID/path, expected revision, operation and complete proposed content; approval rechecks the revision and appends history, while a conflict refuses to overwrite newer content. New notes receive new IDs and deletion uses trash/recovery. Future external connectors require explicit Online mode and bounded connector scope. Markdown skill guidance never grants executable authority.

## Acceptance scenario

With an offline-prepared local model and a saved note, ask: “Search Memory for my note about the emergency water reserve, read the matching note and tell me the exact amount.” Acceptance requires a successful search receipt, a read of that exact result, a generated answer supported by the read, an exact source citation, and no external requests. A one-shot search excerpt or a mocked answer is a failure. Test on PC and report phone verification separately.
