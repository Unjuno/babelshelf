## Agent autonomy boundary · 2026-10-28

BabelShelf is the interface between the user and the selected model, not a pre-scripted workflow that should stop after an arbitrary number of reasoning steps. The default agent profile therefore has no fixed tool-call count. A user may choose a finite profile limit; otherwise the run ends when the model returns a final action, the user stops it, an unrecoverable application/persistence error occurs, or the selected model can no longer fit the retained request and evidence in its real context. A registered tool's expected operation failure is returned as a typed, evidence-free result so the model can choose another route or report the failure. Context exhaustion may still produce an explicitly partial answer from evidence already obtained. It must not pretend the task completed. The 128-event limit applies to inline `turn.activity`; production persistence pages later events instead of imposing a total 128-event receipt limit. Accordingly, the paged product route does not currently derive a call ceiling from event storage. `activityBoundedToolBudget` and its reserve apply only where paged persistence is unavailable; that compatibility path budgets four activity receipts per tool attempt and reserves terminal plan/answer receipts plus the bounded repair attempts. Actual storage quota and persistence errors remain terminal. Optional cumulative text-generation token/time budgets are now implemented per Send in turn-inference-budget.ts and applied by submission-workflow.ts. Null defaults preserve unlimited profile behavior; these are generation budgets, not total task wall-time limits. Model loading, token counting and tools are outside this timer. Paged receipt preservation is covered by controlled tests; live-model long-sequence and quota behavior remain open.

This does not give the model a general host shell or bypass the browser sandbox. The model chooses among tools actually registered for the turn; schemas and local runtime contracts still apply. Storage revisions, source identity, cancellation, and the app's write/approval rules remain owned by deterministic application code. Keep hard restrictions only where they enforce an actual runtime/resource or data-integrity boundary; do not add fixed action-count or workflow-shape limits merely to make the model behave predictably.

Other registered CPU/WASM model routes remain independent. The loaded runtime reports CPU/WASM when the desktop fallback occurred. Model preparation checks and Developer diagnostics now request the same high-performance preference as inference, reducing the chance that a power-saving adapter is checked while a high-performance adapter is used at load. This is only a browser hint: it may be ignored, and the separately probed adapter is not proof of the adapter used by inference. Repeated load of the same resident model returns the existing backend without rereading the OPFS model file or unloading the session. These controlled tests establish routing and cleanup contracts, not iPhone/Android model fit, real GPU placement, performance, or warm-turn latency.

Keep 8K as the current fresh-install default until a real browser-runtime comparison supports changing it. If a future default is raised, compare first-response latency, memory, sustained generation and source retention at 8K/32K/256K on the actual Wllama WebGPU product path. A requested context must either load as requested or fail visibly; do not silently replace it with a smaller context. Preserve existing user selections.

## Agent and model direction · 2026-10-28

The user-facing goal is an agent that connects the user to their local knowledge and completes natural-language tasks by choosing among installed local models and configured tools. Source scope determines which evidence may support an answer; it does not hide configured tools merely because an attachment or file is open. The app still owns data identity, model/tool interfaces, cancellation, durable history and transactional consistency. This leaves the agent room to plan while keeping persisted knowledge verifiable and recoverable.

The default profile has no configured tool-call limit; the UI's “No profile limit” means this optional limit is unset. Individual tool results remain bounded to 8,000 characters. Each inference returns one plan: a tool call, a batch that the host executes sequentially with per-call validation, or a final application action. There is no fixed eight-call batch ceiling. The full active local read-only catalog remains available across planning steps; the model chooses tool, order, repetition and when to finish. A configured remaining call budget is given to the planner and enforced before any over-budget call executes. Paged receipt persistence allows more than 128 activities; it is not a work-budget enforcement mechanism. When a configured profile budget or context limit ends the run, the model cannot claim an unrun operation occurred; useful prior evidence may still yield a clearly partial grounded answer. Native tool-call planning receives the selected model output allowance (LFM3 currently up to 3,072 tokens), bounded by remaining context; this includes private reasoning, tool syntax and the visible answer. The quarter-context/2,048-token planner ceiling applies to the legacy route without final evidence, not to native LFM3. Both require the minimum planner allocation to fit; detailed evidence-backed legacy replies use the requested response style and remaining context. This removes the former universal 160-token generation cap; actual LFM3 batch adequacy and latency still need verification. Context capacity, Stop, repeated no-progress detection and unrecoverable application/persistence errors are runtime boundaries. They coexist with the optional per-Send generation budgets. Planning, repair and final-answer generation share one budget; omitted token usage charges the requested allowance conservatively, and late previews after expiry are suppressed. General task-time and thermal accounting remain open. Expected registered-tool failures return only `{code: tool_execution}` to the model; their raw exception text is retained neither as tool evidence nor planner context. This follows the tool-result recovery shape used by other tool-calling runtimes without adding an MCP transport. If existing evidence no longer fits, old result bodies are omitted from the planner projection while canonical bounded results remain available to the grounded-answer path; if non-tool context alone cannot fit, planning fails or returns a clearly partial grounded answer when useful evidence already exists. Cross-source questions keep Memory tools available and the text planner active so that current inputs and saved Memory can be retrieved and cited together. This does not prove that every small model will choose the right tools; model choice and actual task completion remain acceptance gates.

Agent-routed Send now captures an ephemeral, immutable `TurnExecutionSnapshot` at the application boundary. Text model/runtime identity, selected role IDs, the copied Harness profile/tool list/budgets, answer style/guidance, available attachment original/reading IDs, and the current `Settings/models.md` and `Settings/harness.md` revision numbers are consumed from that snapshot; mutating caller-owned arrays after Send cannot change the Agent's tool set or budget. The first user-turn/original commit atomically compares those expected settings revisions with the canonical records and the current dialogue in IndexedDB, for both attachment and text-only sends; if another tab changed either model or Harness settings, the draft is retained and the stale turn is refused before planning. Planner/tool activity receipts record the same turn/model/config identity and the actually exposed tool IDs without duplicating the full request or custom guidance. A selected custom tool still records its content hash on the invocation. Separately, preference records use a versioned schema: legacy schema-0/1 values are projected to the current shape without rewriting stored bytes; an invalid current value reads from the newest compatible history entry or factory defaults and is marked invalid; explicit single-record recovery appends the broken/future-schema body to history and creates a new revision. Restore-defaults also creates revisions and refuses tampered managed records. These recovery paths have unit coverage. The turn snapshot is still ephemeral, not a resume record or a durable activated-profile record. Source revisions are acquired and checked by the existing read/answer/CAS operations, not pre-enumerated at Send time. Durable resumable activation and explicit source revision snapshots remain future work where a workflow needs them. Storage remains the final authority for source eligibility, write approval, conflict detection and commit.

## Dependency direction

UI -> application operations -> domain contracts -> local adapters.

Application operations choose scope and sequence. The harness plans only within that scope. Runtime policy selects an already registered/prepared engine and owns acquisition decisions; low-level clients retain Worker and lease ownership. Knowledge operations validate source eligibility, approval and expected versions. The UI presents data/reviews and supplies user actions. Memory definitions may configure behavior but cannot replace authorization, storage integrity, protocol validation or cancellation limits.

A run should pin: request/scope, configuration revision, selected model/runtime revision, tool identities, source revisions, Stop ownership and its typed outcome. Related canonical changes must still be one transaction; splitting repositories must not split an atomic commit.

## Migration order and gates

1. Completed foundations: isolate Send, outcomes, Text/Decision acquisition and scheduled answering. Preserve local transactions and existing interface.
2. Correction-review persistence is implemented for existing note/settings/schedule/tool-source proposals: one versioned local record, exact target/dependency snapshots, explicit resume, atomic approval/receipt/deletion and CAS cancellation. See PENDING-REVIEWS.md. Extend durable recovery separately to capture/new-task reviews; neither startup nor restore may automatically approve or repeat inference.
3. Preserve the two existing boundaries: `preference-records.ts` provides non-destructive legacy projection, last-valid/factory fallback, explicit per-record recovery and revisioned factory restore; `TurnExecutionSnapshot` pins model/Harness values for an in-flight turn and CAS-checks their canonical revisions before its first user/original commit. Remaining work is a durable activated-profile/resume record with validation across restart, if resumable turns require it; do not describe preference recovery as missing or merge it into ordinary preference reads. Keep unsupported future schemas untouched until the user explicitly recovers them.
4. Introduce command/query storage ports, then incremental search. Keep the current store as the transaction implementation during migration. Test conflicts, restore, source references and interrupted rebuild; never rebuild by deleting canonical data.
5. Extend runtime residency only for a measured bottleneck. Optional preload and warm reuse must not acquire missing assets silently, interrupt another active role or claim that browser GPU limits imply model fit.

## Performance measurement contract

The default Quick test remains one exact structured READY smoke. Performance is an explicit option under the same Run tests action: one fixed `prose-128-v1` request, up to 128 output tokens. It records actual input/output tokens, configured route, registered quantization metadata when known, model/runtime revision, load state, Load-call duration, generation duration, available TTFT and runtime-memory counters. Unknown custom tensor IDs are retained as IDs, not guessed quantization names.

No user knowledge, chat history, original files or generated reply text are retained in the report or sent externally. The report is local and manually copyable. Original output is discarded. Missing timings are omitted, not filled with invented zeroes; runtime counters are not total process/driver/device memory. Actual output length may be shorter than the cap. One sample cannot establish sustained speed, heat, quality or iPhone/Android compatibility. Home Screen restart checks still require manual OS actions and cannot prove those actions occurred.

Evidence-backed answers and ordinary dialogue use the same request-length policy, bounded by the selected engine's declared output limit and the prompt's remaining context. Balanced and detailed responses may use all available tokens; explicit requests for brevity remain brief, and explicit requests for detail override the saved concise preference. The first model call receives the full available allowance up to the engine cap, so no product-wide 1,024-token first-segment ceiling shortens otherwise supported answers. If an engine exposes a smaller output limit, continuation may use the remaining context and per-Send generation budget. These are ceilings, not a requirement to fill tokens. The user's requested length, runtime capability, context capacity and per-Send inference budget are the limits. JSON citation metadata consumes the same output budget, so a long answer can still be refused if its output hits the model/runtime limit; the app never splices an incomplete structured result. A bounded consistency retry uses only the output tokens remaining after its revised prompt is counted; an ordinary balanced turn keeps planner headroom separate from the final-answer allowance, while explicit extended requests retain their larger planning reserve. The system instruction must not impose an unconditional concise style that contradicts the saved preference or current request. Source coverage and citation validity remain mandatory when longer answers compete for context; omission or refusal must be explicit rather than silently dropping required evidence.

## Retry visibility · 2026-10-30

A PC use review found that failed repeated sends made one prompt occupy multiple full chat rows, leaving users to scroll past old errors before reaching a later successful answer. `groupRepeatedFailedTurns()` is now a view-only projection: only exact consecutive retries with a failed/stopped activity receipt, no attachment and no partial sources/results are grouped. The latest answer or latest failed attempt remains the main row; earlier attempts are available from an expandable disclosure that opens that turn's activity. Canonical dialogue turns, IDs, source references and immutable receipts are not rewritten. In particular, matching wording alone never merges successful turns, changed prompts, attachment-bearing turns, partial search outcomes, or statuses without a failure receipt. Tests cover projection invariants and a PC browser fixture that verifies the activity link and all original stored turns. This reduces repeated-scroll friction; it does not recover a failed inference or prove model reliability. Build/test evidence: `a08f3a9505b210dd`, recorded in [TEST-RESULTS.txt](TEST-RESULTS.txt).

## Citation quantity guard · 2026-11-01

An exact source citation can still accompany a changed numeric answer. `checkAnswerConsistency` rejects explicit English/Japanese water-volume answers that conflict with cited excerpts, handles litres/millilitres and common Japanese integer numerals, and binds a named water value to its nearest recognized water/fuel label. A water-volume answer also binds to the one cited note whose title is explicitly named in the question; an amount in a second citation cannot mask that note's conflicting value. When titles overlap, the longest matching title wins; duplicate titles remain ambiguous and are not used for source-specific binding. If zero or multiple distinct cited note titles are named, the all-cited-values behavior remains, so multi-source entity/value assignments are still not generally checked. This remains a narrow lexical guard, not semantic entailment or validation of other numeric domains. A rejected answer does not reach save review. Deterministic tests cover overlapping titles; full live-model behavior and phone quality remain unverified.

## Full-cycle acquisition order · 2026-11-04

An iPhone device report stopped at `runtime-setup` after 29 minutes while the selected LFM3 model files were still absent (`filesPresent:false`, `assetState:not-run`). The full-cycle check acquired the separate LFM3 runtime before preparing the roughly 1.05 GB model, so useful model preparation had not started. The flow now verifies/prepares the selected model first and checks/downloads its runtime only after the model is locally ready. A failed or stopped model download therefore does not spend network time on an unusable runtime. Progress/report fields continue to separate model and runtime bytes and durations. This ordering fix does not prove that an iPhone runtime download or model load is fast, and does not replace a device rerun if a current-build runtime still stalls.
