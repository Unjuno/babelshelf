# Architecture review and target — 2026-10-28

Scope: current local application after the Send boundary, shared model acquisition and one-button device-test changes. This is a code/design review, not proof of all model/device combinations. Accepted UI, canonical knowledge and history remain invariants.

## Agent autonomy boundary · 2026-10-28

BabelShelf is the interface between the user and the selected model, not a pre-scripted workflow that should stop after an arbitrary number of reasoning steps. The default agent profile therefore has no fixed tool-call count. A user may choose a finite profile limit; otherwise the run ends when the model returns a final action, the user stops it, an unrecoverable application/persistence error occurs, or the selected model can no longer fit the retained request and evidence in its real context. A registered tool's expected operation failure is returned as a typed, evidence-free result so the model can choose another route or report the failure. Context exhaustion may still produce an explicitly partial answer from evidence already obtained. It must not pretend the task completed. The 128-event limit applies to inline `turn.activity`; production persistence pages later events instead of imposing a total 128-event receipt limit. Accordingly, the paged product route does not currently derive a call ceiling from event storage. `activityBoundedToolBudget` and its reserve apply only where paged persistence is unavailable. Actual storage quota and persistence errors remain terminal. Cumulative token/compute-time accounting is not implemented, and context/output bounds are per generation rather than a whole-turn compute budget. Paged receipt preservation is covered by controlled tests; live-model long-sequence and quota behavior remain open.

This does not give the model a general host shell or bypass the browser sandbox. The model chooses among tools actually registered for the turn; schemas and local runtime contracts still apply. Storage revisions, source identity, cancellation, and the app's write/approval rules remain owned by deterministic application code. Keep hard restrictions only where they enforce an actual runtime/resource or data-integrity boundary; do not add fixed action-count or workflow-shape limits merely to make the model behave predictably.

Repeated load of the same resident model returns the existing backend without rereading the OPFS model file or unloading the session. If a future default is raised, compare first-response latency, memory, sustained generation and source retention at 8K/32K/256K on the actual Wllama WebGPU product path. A requested context must either load as requested or fail visibly; do not silently replace it with a smaller context. Preserve existing user selections.

## Agent and model direction · 2026-10-28

The user-facing goal is an agent that connects the user to their local knowledge and completes natural-language tasks by choosing among installed local models and configured tools. Source scope determines which evidence may support an answer; it does not hide configured tools merely because an attachment or file is open. The app still owns data identity, model/tool interfaces, cancellation, durable history and transactional consistency. This leaves the agent room to plan while keeping persisted knowledge verifiable and recoverable.

The default profile has no configured tool-call limit; the UI's “No profile limit” means this optional limit is unset. Individual tool results remain bounded to 8,000 characters. Each inference returns one plan: a tool call, a batch that the host executes sequentially with per-call validation, or a final application action. There is no fixed eight-call batch ceiling. The full active local read-only catalog remains available across planning steps; the model chooses tool, order, repetition and when to finish. A configured remaining call budget is given to the planner and enforced before any over-budget call executes. Paged receipt persistence allows more than 128 activities; it is not a work-budget enforcement mechanism. When a configured profile budget or context limit ends the run, the model cannot claim an unrun operation occurred; useful prior evidence may still yield a clearly partial grounded answer. Planner output receives a context-aware budget: up to one quarter of the selected context, bounded by remaining capacity and a 2,048-token ceiling, with 160 tokens required to fit a plan at all. This removes the former universal 160-token generation cap; actual LFM3 batch adequacy and latency still need verification. Context capacity, Stop, repeated no-progress detection and unrecoverable application/persistence errors are runtime boundaries. They do not replace cumulative token/compute-time accounting, which remains open. Expected registered-tool failures return only `{code: tool_execution}` to the model; their raw exception text is retained neither as tool evidence nor planner context. This follows the tool-result recovery shape used by other tool-calling runtimes without adding an MCP transport. If existing evidence no longer fits, old result bodies are omitted from the planner projection while canonical bounded results remain available to the grounded-answer path; if non-tool context alone cannot fit, planning fails or returns a clearly partial grounded answer when useful evidence already exists. Cross-source questions keep Memory tools available and the text planner active so that current inputs and saved Memory can be retrieved and cited together. This does not prove that every small model will choose the right tools; model choice and actual task completion remain acceptance gates.

Agent-routed Send now captures an ephemeral, immutable `TurnExecutionSnapshot` at the application boundary. Text model/runtime identity, selected role IDs, the copied Harness profile/tool list/budgets, answer style/guidance, available attachment original/reading IDs, and the current `Settings/models.md` and `Settings/harness.md` revision numbers are consumed from that snapshot; mutating caller-owned arrays after Send cannot change the Agent's tool set or budget. The first user-turn/original commit atomically compares those expected settings revisions with the canonical records and the current dialogue in IndexedDB, for both attachment and text-only sends; if another tab changed either model or Harness settings, the draft is retained and the stale turn is refused before planning. Planner/tool activity receipts record the same turn/model/config identity and the actually exposed tool IDs without duplicating the full request or custom guidance. A selected custom tool still records its content hash on the invocation. Separately, preference records use a versioned schema: legacy schema-0 values are projected to the current shape without rewriting stored bytes; an invalid current value reads from the newest compatible history entry or factory defaults and is marked invalid; explicit single-record recovery appends the broken/future-schema body to history and creates a new revision. Restore-defaults also creates revisions and refuses tampered managed records. These recovery paths have unit coverage. The turn snapshot is still ephemeral, not a resume record or a durable activated-profile record. Source revisions are acquired and checked by the existing read/answer/CAS operations, not pre-enumerated at Send time. Durable resumable activation and explicit source revision snapshots remain future work where a workflow needs them. Storage remains the final authority for source eligibility, write approval, conflict detection and commit.

### Implementation sequence

1. Introduce a typed immutable `TurnExecutionSnapshot` at the application boundary and make planner/tool/result receipts identify that same snapshot. Preserve existing persistence records; this is execution metadata, not a knowledge-store migration.
2. Preserve the no-default-call-ceiling policy while keeping storage and work budgets distinct. Standard and Source-first have no explicit fixed call-count ceiling; saved finite profile limits remain supported. Production paged activity storage has no 128-event total ceiling, so the legacy activity-derived tool budget applies only when paged persistence is unavailable. Activity detail now derives an observed planner-token/model-time and registered-tool-duration rollup from persisted receipts; it does not enforce a cumulative budget and does not include separately traced answer routes that expose no inference receipt. Per-result size and selected-runtime context fitting do not constitute a per-turn compute budget. Live-model behavior during long varied tool sequences is unverified.
3. Context fitting uses the selected engine manifest and actual prompt token counting. Planner generation now has a context-aware output budget rather than a fixed 160-token cap; overflow handling omits old result bodies from the transient planner view while preserving canonical history for the final grounded answer. Real LFM3 batches and request-specific latency need measurement. Never substitute an advertised model context or another engine's manifest for the selected runtime's actual limit.
4. Continue LFM3 acceptance: Q4 has one PC offline grounded-answer/source/reviewed-save path; Q8 has one PC offline grounded-answer/source path and is now selectable from the built-in catalog. Next verify a real structured tool call, Stop/retry, warm reuse, Q8 reviewed save, and a same-task Q4/Q8 comparison for quality and resource use. Keep Q4 as fresh-install default until those results justify a change; preserve old selections.
5. Verify an end-to-end local task with multiple source reads, a detailed cited answer, explicit reviewed note save, Stop, and a cold offline rerun. Use a real selected model for behavioral claims; controlled adapter tests check boundaries only.

Step 1 is implemented for the ephemeral per-turn snapshot, with CAS validation before the first user/original commit; it is not a durable activation or resume record. Preference migration/recovery is implemented separately: schema-0 projection is read-time only, fallback is visibly invalid, and repair/default restoration appends revisions rather than erasing broken bytes. Step 2 supports optional finite profile limits, paged activity receipts, and an observed work rollup in Activity detail; the rollup is informational and the paged production route still has no default total-call cap or cumulative stop budget. It does not cover separate inference routes that do not emit planner metrics. Step 3 counts against the selected runtime context and retains its minimum plan-fit threshold. Exact current gates and evidence are in [REMAINING-GATES.md](REMAINING-GATES.md) and [LFM3-RUNTIME-SPIKE.md](LFM3-RUNTIME-SPIKE.md). ## Dependency direction

UI -> application operations -> domain contracts -> local adapters.

Application operations choose scope and sequence. The harness plans only within that scope. Runtime policy selects an already registered/prepared engine and owns acquisition decisions; low-level clients retain Worker and lease ownership. Knowledge operations validate source eligibility, approval and expected versions. The UI presents data/reviews and supplies user actions. Memory definitions may configure behavior but cannot replace authorization, storage integrity, protocol validation or cancellation limits.

A run should pin: request/scope, configuration revision, selected model/runtime revision, tool identities, source revisions, Stop ownership and its typed outcome. Related canonical changes must still be one transaction; splitting repositories must not split an atomic commit.

## Migration order and gates

1. Completed foundations: isolate Send, outcomes, Text/Decision acquisition and scheduled answering. Preserve local transactions and existing interface.
2. Correction-review persistence is implemented for existing note/settings/schedule/tool-source proposals: one versioned local record, exact target/dependency snapshots, explicit resume, atomic approval/receipt/deletion and CAS cancellation. See PENDING-REVIEWS.md. Extend durable recovery separately to capture/new-task reviews; neither startup nor restore may automatically approve or repeat inference.
3. Preserve the two existing boundaries: `preference-records.ts` provides non-destructive legacy projection, last-valid/factory fallback, explicit per-record recovery and revisioned factory restore; `TurnExecutionSnapshot` pins model/Harness values for an in-flight turn and CAS-checks their canonical revisions before its first user/original commit. Remaining work is a durable activated-profile/resume record with validation across restart, if resumable turns require it; do not describe preference recovery as missing or merge it into ordinary preference reads. Keep unsupported future schemas untouched until the user explicitly recovers them.
4. Introduce command/query storage ports, then incremental search. Keep the current store as the transaction implementation during migration. Test conflicts, restore, source references and interrupted rebuild; never rebuild by deleting canonical data.
5. Extend runtime residency only for a measured bottleneck. Optional preload and warm reuse must not acquire missing assets silently, interrupt another active role or claim that browser GPU limits imply model fit.

## Performance measurement contract

The default Quick test remains one exact structured READY smoke. Performance is an explicit option under the same Run tests action: one fixed `prose-128-v1` request, up to 128 output tokens. It records actual input/output tokens, configured route, registered quantization metadata when known, model/runtime revision, load state, Load-call duration, generation duration, available TTFT and runtime-memory counters. Unknown custom tensor IDs are retained as IDs, not guessed quantization names.

No user knowledge, chat history, original files or generated reply text are retained in the report or sent externally. The report is local and manually copyable. Original output is discarded. Missing timings are omitted, not filled with invented zeroes; runtime counters are not total process/driver/device memory. Actual output length may be shorter than the cap. One sample cannot establish sustained speed, heat, quality or iPhone/Android compatibility. Home Screen restart checks still require manual OS actions and cannot prove those actions occurred.

Evidence-backed answers and summaries use the same reply-style/explicit-length policy as ordinary dialogue, bounded by the selected engine's remaining context. This replaces the former fixed 128-token answer and 256-token summary reserve. JSON citation metadata consumes the same output budget, so a long answer can still be refused if its output hits the model/runtime limit; the app never splices an incomplete structured result. The system instruction must not impose an unconditional concise style that contradicts the saved preference or current request.

## Retry visibility · 2026-10-30

A PC use review found that failed repeated sends made one prompt occupy multiple full chat rows, leaving users to scroll past old errors before reaching a later successful answer. `groupRepeatedFailedTurns()` is now a view-only projection: only exact consecutive retries with a failed/stopped activity receipt, no attachment and no partial sources/results are grouped. The latest answer or latest failed attempt remains the main row; earlier attempts are available from an expandable disclosure that opens that turn's activity. Canonical dialogue turns, IDs, source references and immutable receipts are not rewritten. In particular, matching wording alone never merges successful turns, changed prompts, attachment-bearing turns, partial search outcomes, or statuses without a failure receipt. Tests cover projection invariants and a PC browser fixture that verifies the activity link and all original stored turns. This reduces repeated-scroll friction; it does not recover a failed inference or prove model reliability. Build/test evidence: `a08f3a9505b210dd`, recorded in [TEST-RESULTS.txt](TEST-RESULTS.txt).
