# Reviewed model corrections

Ordinary saved Markdown notes can be targeted by exact ID/path or one unambiguous filename. Model routing may select `edit`; it cannot commit. Ambiguous/missing targets ask for a full path rather than selecting the first search hit. Registered schedules now use the separate typed patch described below. Settings, Tools, execution/notification logs and other managed/protected/withdrawn records remain unavailable to this adapter. Existing direct editors are unchanged.

The local model selects literal `text.replace`, `text.split_lines`, or a semantic `text.rewrite` proposal for an ordinary note body. Literal operations retain exact-match, Unicode, match-count and output-size checks. Rewrite selection is a separate step: only the selected original body and current instruction enter a second generation, with a768-token output budget and actual tokenizer/context checks. The complete proposed body must be valid JSON, nonempty, changed, well-formed Unicode and at most30,000 UTF-16 code units. Practical model limits are smaller than that validator bound; input plus reserved output must fit the2048-token runtime window. Invalid/truncated output is rejected, never spliced in as a partial rewrite. No regex, path change, target change, metadata mutation or file deletion is accepted from model output.

A proposal holds a fresh ID, current request, complete canonical expected record, before/after body and structured operation result. Inference snapshots the selected canonical record before awaiting; later caller mutation or another-tab edits cannot silently become the base of an older generated proposal. Preparing it writes no knowledge record. Review shows path, version, complete Before and After, Cancel and Save. Only explicit Save calls the approval adapter. A pending review is session-only: reopening preserves the request/status but requires a new proposal, never automatic execution.

Approval uses one IndexedDB read/write transaction over existing schema1 `notes` and `runs` stores. It checks the entire current target against the expected snapshot, replays/validates the exact operation and verifies displayed before/after. A rewrite operation pins the UTF-8 body SHA-256 and before/after UTF-16 counts; approval recomputes these from the exact displayed body. This checks bytes and scope, not semantic correctness: the user must review wording/facts before Save. A single revision and receipt commit together. The receipt key is `ui-v1-correction-<proposal ID>`, type `note-correction`, with target ID/path, request, operation/arguments/result, before/after revision numbers and SHA-256 of the complete after record, timestamp and applied status. Duplicate approvals cannot append twice. IDs, paths, original revisions, aliases, sources and unknown legacy fields are retained. Nothing grants blanket future edit authority.

History reads persisted receipts alongside canonical revision bodies. Explicit Undo requires the complete current record SHA-256 to match the after-record hash, restores the previous body by appending another revision, and updates the receipt to undone in the same notes+runs transaction. Later edits/renames/withdrawal invalidate Undo. Undo never removes a correction revision. It is not an automatic rollback or a permanent delete.

Receipt storage is auxiliary and included/validated by the accepted product's schema2 state brainpack. Legacy schema1 note-only files do not contain receipts. See BACKUP-CONTRACT.md for atomic restore, conflict rejection and remaining media/device recovery gates. A note can remain committed if a later UI/conversation refresh fails; the persisted receipt/history is authoritative and duplicate approval still refuses. Runtime assets and user data are never sent remotely by this adapter. Model/document text is untrusted; it cannot bypass review.

Tests distinguish pure control rules, real IndexedDB atomicity/concurrency and actual local4B generation. Results and build identifiers are recorded in TEST-RESULTS.txt. This contract does not claim mobile-device, full offline restart or general model-language acceptance.

Receipts reference original bodies through immutable canonical revisions rather than copying all historical revisions into every receipt. Rewrite receipts retain only the proposed-body hash and counts, not a second body copy; brainpack validation reconstructs the operation from canonical before/after revisions and rejects forged hashes/counts or mismatched bodies. This avoids quadratic receipt growth. Full expected-record snapshots remain session-only for approval CAS; no historical revision is removed. Hashing reuses the existing local SHA-256 implementation.

Current applied/undo receipts are structured and atomic. Proposal attempts are also recorded in the interactive activity layer, including failure/Stop, without turning their contents into execution authority. Earlier status-only failures remain historical. Approval/Undo writes use the atomic correction receipt; speech/asset and other broader attempt integration remain separate. See HARNESS-ACTIVITY.md.

## Typed schedule changes

An active registered schedule under Schedule may instead propose `schedule.patch`. Only prompt, repeat, time, days, date, monthDay, interval, unit and notify are accepted. The source-only model sees the current Task and current instruction, with actual tokenizer budget/Stop checks; it receives no dialogue, other notes or execution permission. Raw Markdown replacement/rewrite is unavailable for this record type. The merged Task is validated before review, and semantic no-ops/invalid text/unknown fields refuse. Enabled state, timezone, identity, path and arbitrary metadata cannot be changed by this operation. Restored schedules still requiring review and tasks in another device zone must first use the dedicated Schedule review; model proposals cannot remove that quarantine.

The same full Before/After sheet, exact whole-record CAS, duplicate protection and atomic note/receipt transaction apply. The shared typed task revision helper maintains the task definition/cursor as in the Schedule editor; prompt or recurrence changes recompute due state, while notify-only changes retain the occurrence cursor. Existing enabled state is preserved, including a paused or consumed task. A previously enabled task may run its newly approved definition under the existing foreground-only rules after review closes. Review/Save holds a live task-claim gate to avoid same-page execution changing a pending target. Other clients remain subject to the exact snapshot check.

The receipt stores sorted changed-field names and a SHA-256 of the canonical changes, rather than copying a long prompt. Validation reconstructs values from the retained after revision, checks the hash, reapplies them to the before Task and compares the exact operation/body. Pure receipt validation is device-zone independent; it grants no runtime permission. Explicit Undo appends the prior body through the same task revision/cursor helper and requires the complete current record hash; intervening cursor execution, state, edits or metadata changes invalidate it. IDs, original revisions and sources remain intact. Schedule creation from natural language and typed settings/tool edits remain separate pending routes.
