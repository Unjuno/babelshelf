# Tool packages — current user direction

The user's latest direction is executable code paired with a SKILL.md usage file, not Markdown-only tool descriptions or JSON-only definitions. The basic package is SKILL.md plus implementation code. Code can export its argument schema and entry points. A separate machine-readable manifest is optional when identity/version/capabilities/assets need it; do not force a third file when two suffice. The model reads usage guidance; the harness invokes real code and returns typed results. MCP connection code can be an adapter inside a package. Protocol/browser/runtime compatibility must be verified rather than assumed.

Current Tools/*.md are protected explanatory records; actual native tool handlers live in application code. Do not represent a new Markdown/JSON document as an installed executable adapter. Keep existing records/history during migration. Preserve the accepted Memory/Settings UI and local canonical data.

Registration, inspection, prepared assets and execution must stay distinct. Model/document/SKILL content does not grant code-installation, writes, network or future execution permission. Initial packages should wrap the actual connected local search/read/reviewed-capture/correction handlers and preserve their typed inputs/results/approval/CAS behavior. Installing new implementation code is different from adding a definition. Ordinary usage remains offline; no implicit fetch, external personal-data upload or cloud/LAN inference.

This records the architectural direction from the conversation. It is not an implemented plugin loader, verified sandbox, MCP server/client or permission boundary. PWA host capabilities, package execution isolation and MCP transport roles need concrete design and verification before claiming support. No legacy data deletion, arbitrary eval of Memory documents or automatic imported-code execution.

## Memory-defined API and harness configuration (design direction)

The user wants the chat harness and its tools to be extensible through Memory, while keeping a useful standard set. Treat Memory as the editable, versioned configuration surface for an API-like local capability graph: user-facing descriptions, presentation rules, output layouts, model-role bindings, and supported options can be inspected and revised there. A conversation turn is an invocation against the declared interfaces; it is not itself the API definition or a durable session that owns the user's knowledge.

The preferred generation shape is a bounded agent loop: inspect context, choose among registered typed tools, receive canonical results, and continue toward an answer. The application owns the loop budget, cancellation, tool schemas, source pins, and explicit approval for writes. Tool calls are not improvised code; reaching the step limit, a failed tool, or missing preparation must stop clearly rather than fabricate a result.

Keep three layers explicit:

1. **Editable configuration in Memory:** users can customize descriptions, response presentation/layout, a single bundled default theme's constrained design tokens, model-role selection, supported pipeline options, and multiple built-in pipeline/profile templates as editable starting points. The model may propose changes to these user-configurable records through chat; the app validates them, shows a preview and saves only after explicit approval, with version history and Undo. Built-in defaults remain available and have stable IDs. Customization creates an override/fork rather than silently mutating the protected baseline. Model-generated JavaScript, arbitrary CSS, HTML, or application source is never executed as a theme or response renderer.
2. **Fixed execution contract:** chat orchestration, tool-call protocol, typed adapter input/output schemas, identity/source validation, cancellation, capability checks and approval gates remain application-owned. A Memory definition can select and configure only capabilities the current app registered. Unsupported fields or operations fail visibly; neither a model nor a definition can widen execution authority by declaring it.
3. **Implementation:** trusted bundled adapters execute typed operations. Adding a definition is not code installation. Imported scripts are not evaluated; MCP transport or user code requires a separately implemented and reviewed adapter boundary.

Provide **Restore defaults** for the editable configuration and response presentation. It resets only recognized configuration records to the app's current bundled defaults, through an explicit review/confirmation and one atomic, version-preserving transaction. It must retain knowledge, user files, histories, sources, tools and active model assets; never implement recovery by clearing IndexedDB. Malformed or incompatible configuration should fall back to a safe built-in presentation and expose a recovery action, not disable access to Memory.

This lets users customize how responses are presented and how supported local capabilities are composed from several validated starting profiles without making core dispatch or safety rules mutable and without pretending Markdown is executable code. Chat-driven changes are constrained data edits (validated tokens/layout schemas), not direct source-code edits. It leaves a path for advanced packages to publish typed interfaces like APIs, including MCP-backed adapters later, while keeping model output and retrieved documents untrusted. The user's data stays local unless a separately reviewed, explicit network-capable adapter is installed and invoked. Do not claim this configurable registry or generalized API layer is implemented yet; current Tools records and package registry remain the narrower bundled design described above.

## Unit79 registry design and acceptance

Centralize trusted bundled module registration with code/SKILL/shared dependency bytes, not Memory-defined registration. A pure registry validates IDs, positive versions, read-only/network-none policy, relative source names, entry/SKILL presence, duplicate IDs and callable entry. ## Unit80 — bounded read-only loop on the normal planner route

`src/agent-loop.ts` defines the orchestration contract for sequential model-selected tool calls: only app-supplied capabilities explicitly marked `readOnly:true` and `network:'none'` are eligible; every plan/result boundary checks cancellation; an application-owned three-call limit prevents runaway loops; malformed/unknown calls, oversized or unserializable results, Stop and adapter failures terminate without retry. Tool results are returned as data and must be labelled untrusted when injected into model context. Write proposals, user-installed code, MCP transport and network tools are outside this loop.

`planDialogueAgent()` is wired into ordinary Send when the existing router chooses the text-planner route. It exposes only the registered local `memory.search` and `memory.read` packages, and only when the request has no current attachment or explicitly opened working file. Tool results are projected to bounded exact excerpts; source refs are reconstructed only from those canonical results and passed as pinned evidence to answer generation. The loop never performs a second search after planning, and stale source revisions reject rather than falling back to historical pins. Each planner/tool step is recorded through the existing on-demand activity path with its package identity. This route does not activate for direct deterministic/Decision actions, and is not an always-running agent.

The focused tests exercise sequential calls, exact history handoff, direct finalization, invalid/unknown calls, cancellation, adapter failure, call-limit exhaustion, result bounds, pinned evidence and no historical/fresh-search fallback. This implements a narrow read-only loop in the normal planner route; it does not add write/delete, custom executable packages, MCP transport, network tools, or a universal multimodal agent. Public-site or real-device verification of this code is not implied by the Node tests.
