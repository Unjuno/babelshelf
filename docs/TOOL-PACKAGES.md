# Tool packages — current user direction

The user's latest direction is executable code paired with a SKILL.md usage file, not Markdown-only tool descriptions or JSON-only definitions. The basic package is SKILL.md plus implementation code. Today, SKILL.md carries the declarative input schema and bounded capability list; `tool.js` implements the entry point. This keeps inspection and validation from executing user source just to discover a contract. A separate machine-readable manifest is optional when identity/version/capabilities/assets need it; do not force a third file when two suffice. The model reads usage guidance; the harness invokes real code and returns typed results. MCP connection code can be an adapter inside a package only when a separately approved, implemented transport grants it; current user packages do not have network access. Protocol/browser/runtime compatibility must be verified rather than assumed.

Current Tools/*.md are protected explanatory records; actual native tool handlers live in application code. Do not represent a new Markdown/JSON document as an installed executable adapter. Keep existing records/history during migration. Preserve the accepted Memory/Settings UI and local canonical data.

Registration, inspection, prepared assets and execution must stay distinct. Model/document/SKILL content does not grant code-installation, writes, network or future execution permission. Initial packages should wrap the actual connected local search/read/reviewed-capture/correction handlers and preserve their typed inputs/results/approval/CAS behavior. Installing new implementation code is different from adding a definition. Ordinary usage remains offline; no implicit fetch, external personal-data upload or cloud/LAN inference.

This records the architectural direction and current implementation boundaries. BabelShelf now has a constrained local custom-code route described below, but this is not a general plugin loader, verified hostile-code sandbox, MCP server/client or broad permission system. PWA host capabilities, package isolation and MCP transport roles still need concrete design and verification. No legacy data deletion, arbitrary eval of general Memory documents or automatic package execution merely because source files exist.

## Custom package intake foundation (2026-10-21)

The canonical path contract now admits one inert JavaScript entry per `user.*` package at `Tools/user.<name>/tool.js`, alongside its `SKILL.md`. Export returns exact UTF-8 source as `tool.vN.js` without Markdown wrapping. Bundled `.ts` source paths retain their existing rules. This is a storage/export capability only; it does not mark a package installed or add it to the active tool registry.

`src/custom-tool-package.ts` inspects the two source records as data. `SKILL.md` starts with bounded JSON front matter containing only `id`, `version`, `title`, a closed scalar-object input schema, and capabilities chosen from local `memory.search`, `memory.read`, and `math.calculate`; Markdown usage instructions follow the closing delimiter. The inspector rejects duplicate/missing files, path/ID mismatch, unknown permission fields, schema features outside the supported subset and source larger than 32 KiB for code / 12 KiB for the skill. It computes SHA-256 over the exact metadata, usage text and code. It never parses or evaluates JavaScript. This is an intake validator, not a plugin runner or a sandbox.

Settings → Custom tools can import exactly two local files named `SKILL.md` and `tool.js`. The app bounds their size before reading, validates the closed metadata/schema and normalized `Tools/user.<id>/` paths, then stores the exact pair as ordinary versioned Memory files. A conflicting ID/path or malformed pair is refused; import never overwrites, selects, or executes code. The user can open both files in Memory and enable the tool only through a reviewed harness-profile change. Imports from archives, external URLs, arbitrary entry files and packages requesting network/write capabilities are not supported.

The same editor can draft a package with the selected text model. Drafting is available only while that exact local model is already loaded; it does not load or download model assets. `inputSchema` is editable JSON: a closed object with 1–8 named string, number, integer or boolean fields, bounded by the application validator. The model may propose multiple typed fields; users can also change the schema and code directly. Model output must pass the same closed schema, path and size validation as a hand-written package. Suggested capabilities are shown but remain unchecked until the user explicitly selects them. The model proposal fills editable fields; only the user's separate Save action stores the pair, and Save still does not enable or execute it. The generated source remains untrusted and may be wrong; package code has no network/write permissions and only runs after profile selection through the bounded runtime. Model drafting itself has unit coverage, but no real-model tool-generation accuracy claim is made.

The synchronous source validator lives separately in `src/custom-tool-validation.ts` because reviewed edits to a `Tools/user.*` file must be revalidated inside the same synchronous IndexedDB transaction that checks and commits the correction. The package creator and asynchronous hashing inspector are loaded on demand when a package is saved or selected; they are not part of the ordinary app startup chunk. This is a transfer/parse boundary, not a claim of measurable startup-time improvement.

Example `SKILL.md` header:

```text
---
{"id":"user.date-format","version":1,"title":"Date format","inputSchema":{"type":"object","required":["value"],"additionalProperties":false,"properties":{"value":{"type":"string","minLength":1,"maxLength":100}}},"capabilities":["memory.read"]}
---
Describe when to use this tool and its limits.
```

The paired `tool.js` is retained and exported exactly. The prototype now includes an opt-in runtime function at `src/custom-tool-runtime.ts` backed by `quickjs-emscripten` 0.32.0 (MIT). It creates a disposable module Worker and a fresh QuickJS WASM runtime, passes JSON input, permits only declared local `memory.search`/`memory.read` RPCs or the deterministic `math.calculate` adapter, defaults to an 8 MiB VM heap / 256 KiB stack / 750 ms instruction deadline / 8 KiB result, caps source at 32 KiB, and terminates the Worker after a bounded wall-clock timeout. A run may issue at most eight capability calls, with no more than two unresolved calls at once, limiting load on Memory and calculation bridges as well as the isolated VM. Stop, wall-clock expiry, or an exceeded budget terminates the Worker and aborts active host signals; the app's canonical IndexedDB read path uses the signal to abort its transaction. The VM has no browser `fetch`, DOM, storage, or process globals; the worker itself exposes only declared capability bridges. Function entries are synchronous; declared Memory reads and calculations appear synchronous inside the VM while the Worker brokers them outside it. The calculator accepts only its bounded arithmetic grammar and creates no source citations. Output is JSON data and remains untrusted.

`src/custom-tool-adapter.ts` now validates invocation arguments against the inspected closed input schema and adapts a package into the common immutable registry using `.js` entry identity. It brokers only the package's declared local search/read/calculation capabilities, marks the package read-only/network-none, and sends source to the isolated runtime rather than evaluating it in the app realm. Focused tests cover schema rejection, registry identity, authority narrowing, and undeclared capability rejection.

The exact `Tools/user.<id>/tool.js` path is now permitted in Memory alongside `Tools/user.<id>/SKILL.md`; other user code paths are still rejected or stored as Markdown. These records remain in the existing IndexedDB knowledge database. Settings → Custom tools opens the package folder and `Settings/harness.md` profile, and offers an explicit local-runtime check/preparation action. Custom IDs must be selected in a profile before the planner receives them. The normal send path rebuilds the selected registry from the current Memory snapshot, re-inspects the paired files, and runs only the bounded read-only package adapter. The agent prompt labels package usage text untrusted. Tool results remain untrusted and do not independently create source citations.

When a selected custom tool invokes its declared local `memory.search` or `memory.read` capability, the application now observes the canonical host response outside the QuickJS result channel and may use those exact returned source ranges for the final grounded answer. Arbitrary fields returned by custom JavaScript still cannot mint or alter citations. The observation accepts only structurally valid current-record IDs/revisions/ranges and is bounded to at most 12 references / 24,000 characters; host results that exceed the runtime's 24,000-byte capability response limit produce no captured evidence. The normal answer path revalidates every reference against current canonical records and refuses stale, withdrawn or mismatched source bytes. This proves source handoff logic in tests, not that a real model reliably chooses or uses a custom tool.

QuickJS Worker and its four emitted `emscripten-module-*.wasm` assets are marked as the optional `custom-tools` runtime, so initial PWA shell installation does not fetch those bytes. Settings preparation acquires only those build-pinned assets when Downloads are enabled; with Downloads off, the action checks local cache only. Send never silently acquires a missing runtime and fails closed until it is prepared. The product-worker cache harness verifies shell exclusion, explicit acquisition and later local serving. This is not an adversarial-runtime guarantee: browser/QuickJS vulnerabilities and host availability cannot be ruled out. Desktop Chromium tests pass; iOS Safari, repeated worker cleanup under device memory pressure, thermal behavior and physical PWA offline cold restart remain unverified.

The bundled tool host now exposes `search(query)`, `resolve(query)` and cancellation checking; it no longer provides an all-record `views()` method to tool implementations. `resolve` returns exact ID/path matches first, then bounded basename matches, and refuses an overly ambiguous basename so callers can use a full path or ID. Its fixed record projection contains only ID, path, version and current body; conflicting duplicate IDs/paths fail closed instead of passing multiple records. This narrows the interface future isolated packages would receive, but bundled handlers are still trusted application code; it is not a sandbox or user-code installer.

## Reviewed profile selection

Settings → Assistant → Profile lists the profiles from the canonical `Settings/harness.md` record. Choosing a profile opens the shared correction review with before/after tool lists and call/result limits; Cancel keeps the current profile. Save uses the same atomic compare-and-swap, revision history and Undo receipt as a chat-proposed settings change. It stays on Assistant after a direct UI save. The UI does not maintain a separate profile registry.

When a proposed active profile uses custom packages, both source records for each selected package are validated as inert data and pinned in the pending proposal. Their exact canonical snapshots are checked inside the approval transaction. Changing or removing a source while review is open refuses approval; reviewing again captures the new files. The review exposes the pinned source bytes on demand. Chat-proposed active-profile or profile-definition changes use the same dependency check. Selection does not prepare a runtime or execute code; execution still rebuilds and validates the selected registry on the next request.

Historical receipt verification is separate from preparing a new change. Backups verify the exact recorded transformation and immutable tool metadata without requiring that an old package is currently available or executable. This preserves history without treating restore as execution approval. Live correction approval retains source-pair and dependency checks.

## Memory-defined API and harness configuration (partly implemented)

The user wants the chat harness and its tools to be extensible through Memory, while keeping a useful standard set. Treat Memory as the editable, versioned configuration surface for an API-like local capability graph: user-facing descriptions, presentation rules, output layouts, model-role bindings, and supported options can be inspected and revised there. A conversation turn is an invocation against the declared interfaces; it is not itself the API definition or a durable session that owns the user's knowledge.

The preferred generation shape is a bounded agent loop: inspect context, choose among registered typed tools, receive canonical results, and continue toward an answer. The application owns the loop budget, cancellation, tool schemas, source pins, and explicit approval for writes. Tool calls are not improvised code; reaching the step limit, a failed tool, or missing preparation must stop clearly rather than fabricate a result.

Keep three layers explicit:

1. **Editable configuration in Memory:** users can customize descriptions, response presentation/layout, a single bundled default theme's constrained design tokens, model-role selection, supported pipeline options, and multiple built-in pipeline/profile templates as editable starting points. The model may propose changes to these user-configurable records through chat; the app validates them, shows a preview and saves only after explicit approval, with version history and Undo. Built-in defaults remain available and have stable IDs. Customization creates an override/fork rather than silently mutating the protected baseline. Model-generated JavaScript, arbitrary CSS, HTML, or application source is never executed as a theme or response renderer.
2. **Fixed execution contract:** chat orchestration, tool-call protocol, typed adapter input/output schemas, identity/source validation, cancellation, capability checks and approval gates remain application-owned. A Memory definition can select and configure only capabilities the current app registered. Unsupported fields or operations fail visibly; neither a model nor a definition can widen execution authority by declaring it.
3. **Implementation:** trusted bundled adapters execute typed operations. Adding a definition is not code installation. The separately reviewed `user.*` package route is now implemented: importing or editing stores inert source; it runs only after explicit profile selection, through the bounded QuickJS adapter with declared local memory search/read callbacks. This is not arbitrary Memory-document evaluation. A general MCP transport remains unimplemented and requires a separately designed and reviewed adapter.

Provide **Restore defaults** for the editable configuration and response presentation. It resets only recognized configuration records to the app's current bundled defaults, through an explicit review/confirmation and one atomic, version-preserving transaction. It must retain knowledge, user files, histories, sources, tools and active model assets; never implement recovery by clearing IndexedDB. Malformed or incompatible configuration should fall back to a safe built-in presentation and expose a recovery action, not disable access to Memory.

This lets users compose supported local capabilities from validated profiles without making core dispatch or safety rules mutable and without pretending Markdown alone is executable code. `Settings/harness.md` provides versioned `standard`, `source-first`, and `conversation` profiles that select registered read-only tools and reduce fixed call/result budgets. Unknown fields/tools and widened limits are rejected; Restore defaults preserves the profile history. Chat may propose profile changes through Before/After correction review, version history and Undo. Paired user `SKILL.md`/`tool.js` packages are supported by the normal planner when explicitly selected in the profile; source is re-inspected and run in the bounded QuickJS worker described above. Packages may declare local search/read or deterministic arithmetic, and receive no undeclared bridge.

### Chat-assisted custom-tool source correction

When the user opens a `Tools/user.<id>/SKILL.md` or `tool.js` file and requests a correction in chat, the selected model may propose a complete replacement for that one file. The normal correction sheet shows the full Before/After and requires explicit Save; Cancel leaves the current source untouched. The proposal and commit both validate the exact paired package structure. For `SKILL.md`, chat may change the bounded `inputSchema` and usage instructions; ID, package version, title, capability list and all other metadata remain fixed. A schema change is a contract change only: it does not update `tool.js`, so the user may need a separate paired-code correction and should run Test tool on the saved source/input before relying on it. Both revisions retain the exact companion-file compare-and-swap dependency. Tool code is stored as source and is never run while generating, reviewing, or saving a proposal. The review warns that if the package is already selected in the active harness, the approved revision may be executed by a later matching request. Normal revision history and Undo apply. This is code editing, not code execution approval or a claim that generated source is correct; users should inspect the complete diff and use the existing bounded runtime behavior.

The profile flow and chat-assisted Before/After source correction are implemented, but there is no archive import/preview wizard, editable theme/output renderer, arbitrary model-role runtime binding, or MCP transport. Current custom packages do not receive network or write capabilities; the QuickJS boundary is not claimed to be hostile-code-proof.

## Unit80 — bounded read-only loop on the normal planner route

`src/agent-loop.ts` defines the orchestration contract for sequential model-selected tool calls: only app-supplied capabilities explicitly marked `readOnly:true` and `network:'none'` are eligible; every plan/result boundary checks cancellation; an application-owned three-call limit prevents runaway loops; malformed/unknown calls, oversized or unserializable results, Stop and adapter failures terminate without retry. Tool results are returned as data and must be labelled untrusted when injected into model context. Write proposals, user-installed code, MCP transport and network tools are outside this loop.

The loop now takes a JSON snapshot of each bounded tool result and keeps a separate snapshot of its arguments. A handler changing its input object, or a planner changing the history it receives, cannot alter the receipt used by later planning and citation validation. This fixes an evidence-identity boundary; it does not expand the model context window, add a new tool, or prove the model chooses the right tool.

Custom tool input schemas are now also carried from the validated `SKILL.md` metadata into the active registry and the planner prompt. The model receives the schema as data alongside the usage guide, so it can form the correct argument object for that package. The application still checks the exact selected tool ID and the adapter revalidates all arguments before execution; the schema is guidance for planning, never authority or a substitute for validation. Built-in tools without a declared schema keep their existing usage-guide contract.

`planDialogueAgent()` is wired into ordinary Send when the existing router chooses the text-planner route. For an unscoped request, it exposes the registered local `memory.search`, `memory.read` and `math.calculate` packages plus explicitly enabled user packages. A current attachment or opened working file uses a restricted registry with only profile-enabled `math.calculate`; the coordinator does not read Memory tool sources, prepare the custom runtime or expose global Memory search/read in that scope. Tool results are projected to bounded exact excerpts or checked arithmetic receipts. For attachment/file calculations, the answer path combines the verified arithmetic with excerpts selected only from the current attachment or pinned file, and cites that original evidence; arithmetic never creates citations or broadens retrieval. The arithmetic verifies the expression's result, not the model's choice of operands or operation. An unscoped calculation-only tool path finishes with the checked expression/result without a second generation. The loop never performs a second search after planning, and stale source revisions reject rather than falling back to historical pins. Each planner/tool step is recorded through the existing on-demand activity path with its package identity. This route does not activate for direct deterministic/Decision actions, and is not an always-running agent.

If a small text model produces malformed citation JSON twice, the answer path has one bounded structured-output recovery only when exactly one current excerpt was selected. The model supplies an answer string that must occur verbatim in that excerpt; the harness attaches the exact excerpt and rechecks its revision. A paraphrase or inferred claim fails, as do zero or multiple excerpts. This limits unsupported recovery but does not prove that an extractive answer is relevant to the question.

A narrowly specified English question of the form “how many minutes before HH:MM is the [subject]?” uses exact local arithmetic when one current original excerpt contains one time linked to the same subject's stated start. The original excerpt remains the citation. Multiple times, missing subject binding, an overnight/negative difference, or stale evidence fall back or fail rather than being treated as exact. This avoids asking a small model to do simple time subtraction while leaving broader scheduling language to the normal answer path.

The focused tests exercise sequential calls, exact history handoff, direct finalization, invalid/unknown calls, cancellation, adapter failure, call-limit exhaustion, result bounds, pinned evidence and no historical/fresh-search fallback. The planner route also accepts explicitly profile-enabled `user.*` read-only local packages under the custom runtime described above. This does not add package writes/deletes, MCP transport, network tools, or a universal multimodal agent. Public-site or real-device verification is not implied by the Node tests.

## Calculator capability extension (2026-10-24)

Settings → Custom tools exposes the registered local `math.calculate` capability alongside Memory search/read. A desktop Chromium Settings → Memory → Test tool flow selects the capability, saves an inert package, tests it through the isolated QuickJS runtime against the app-owned calculator, confirms `6 * 7` returns `42`, and confirms the active Standard profile remains unchanged. The package receives only its declared bridge and remains disabled until separately selected in a harness profile.
