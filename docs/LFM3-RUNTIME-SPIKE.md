# LFM3 browser runtime spike · 2026-10-28

Current implementation notes are below; the original spike and dated attribution sections preserve historical evidence. For current release status use [REMAINING-GATES.md](REMAINING-GATES.md).

## Native agent reasoning · 2026-10-30

Native LFM3 tool generation now enables the model's thinking template; ordinary non-native operations retain their prior setting. Count and generation share the same template options. Current-call reasoning is bounded transient context for subsequent tool steps, excluded from displayed answers and durable receipts. The native generation allowance follows the selected engine and remaining context (up to 3,072 tokens for this adapter), rather than applying the short visible-reply budget to reasoning and tool syntax together.

A short real Q8 guide-only fixture failed by selecting an unrequested package with thinking disabled. With thinking enabled and the actual remaining-call feedback, it completed a Japanese explanation of purpose, required arguments and read-only scope without executing that package. That run produced 679 output tokens and took 36.51 s prefill plus 79.62 s decode; it is a focused correctness observation, not a matched speed comparison or general task acceptance. The normal-product run with retained dialogue is recorded separately in [TEST-RESULTS.txt](TEST-RESULTS.txt). The older spike's 64-token default-thinking failure does not determine the native agent budget.

## Recurrent prompt reuse · 2026-10-30

The product enables exact-prefix reuse for the pinned LFM3 worker. The first wrapper-only change forwarded native checkpoint controls with `n_ctx_checkpoints=8` and `checkpoint_min_step=8192`, leaving WASM unchanged at that stage. Later actual tool workflows exposed a remaining native checkpoint gap; the current change is described below. `n_cache_reuse=0` still forbids arbitrary KV shifting. A completed operation can seed the next operation in the same worker. Stop, errors and unloading invalidate that eligibility, and native token/checkpoint matching decides whether reuse is possible. This caches intermediate model state, never an answer.

The first actual PC test with ordinary sliding-window storage reused zero tokens despite requesting reuse. The pinned hybrid recurrent/SWA checkpoint selection fell back to recomputation. Full SWA storage (`swa_full=true`) retained the needed attention positions and made native checkpoint restoration work. This preserves the model's attention mask but increases retained KV storage. At the tested 8,192-token context, logs reported 96 MiB non-SWA and 80 MiB full-SWA KV buffers; those values are not total or peak memory. Larger contexts and phone memory fit remain unverified.

In the existing Codex sidebar (Windows x64, Chrome 156.0.0.0, four runtime threads, JSPI route, reported 25/25 GPU-offloaded layers), the cached GREEN fixture reused 625 of 752 input tokens. Prefill was 2,256.945 ms versus 11,982.461 ms for a forced-fresh control with the same input and output (three tokens). End-to-end generation was 2,420.25 versus 12,138.175 ms. A changed native tool schema also matched its fresh control: 624 cached of 821 input tokens, 3,781.27 versus 13,220.541 ms prefill, with the same function and arguments. Actual decode cancellation, subsequent fresh generation and unload/reload all passed; fresh-after-Stop/reload reported zero cached tokens. Both the initial no-reuse result and corrected result are retained in `outputs/lfm3-cache-current.json` and described in TEST-RESULTS.txt.

These are short synthetic comparisons with the already prepared QAD Q4_0 model, not a general fivefold speed claim, Q4/Q8 quality comparison, sustained/thermal result, device-memory guarantee, or physical iOS offline acceptance. Product workflow measurements must be reported separately. Local QA is staged by `scripts/qa/lfm3-backend-comparison.mjs` into the existing preview output without a new browser/profile/server or a model download; it is excluded from the app shell and removed before delivery.

### Long native tool catalogs

The actual Q8 custom-read workflow on build `f7756bfc3e388dab` still reported zero reused tokens at all four steps. Source inspection found that ordinary checkpoints were skipped inside the initial system message. The native chat template embeds function schemas there, so a schema change before the first user-boundary checkpoint left no restorable recurrent state. A targeted 13-function Q4 regression reproduced zero reuse while preserving exact counts and correct function arguments. This differs from the shorter earlier schema sample, whose near-end checkpoint happened to precede the changed schema.

The native patch permits periodically spaced checkpoints inside that long prefix. The adapter retains a maximum of eight and requests a 512-token minimum spacing. Both JSPI and Asyncify WebGPU engines were rebuilt from the pinned source; model weights, user context/output budgets, tool schemas, source guards and save approvals are unchanged. The first native revision was `-checkpoints-1`; source and binary pins are verified together. Measured results belong in the dated test log and current release snapshot; compilation alone is not runtime acceptance.

On local build `6325bd1553fbbed2`, the same Q4 catalog test reused 768 of 2,025 input tokens. Prefill took 22.13 s versus 34.65 s for the identical forced-fresh control (36.1% lower); total generation took 23.73 s versus 36.14 s. Both emitted the same function/arguments with 20 output tokens and exact cached-plus-processed token accounting. The separate actual Stop/reload sequence also passed. These are Windows sidebar/JSPI results; the compatibility engine was rebuilt but not run on Safari. Product-task latency remains a separate measurement.

A subsequent 5,595-token product request exposed FIFO eviction of the early shared checkpoints. Revision `-checkpoints-2` preserves the earliest anchor and removes a densely spaced interior checkpoint when the same eight-entry capacity is full. Duplicate replacement happens before capacity eviction; exact-token restoration and mismatch invalidation remain native responsibilities. No additional checkpoint count or context reduction is introduced. Both engines were rebuilt; the native patch SHA is `d0b1b3d081c0f49560fd61a15a06c7117c5a1620dc6cab1ea240ddc15f2e7a2c`.

On build `8ea1e13d1c1f5b55`, the longer 13-function Q4 fixture changed the permitted answer from GREEN to RED. It reused 768 of 4,832 input tokens, returned RED correctly, and matched the fresh control's function arguments and 19 output tokens. Prefill was 86.96 s versus 103.58 s (16.0% lower); total generation was 89.81 s versus 105.80 s (15.1% lower). All five assertions passed. This one synthetic PC run establishes bounded reuse across a longer changing catalog, not general model quality or phone performance. The separately failed guide-only product request remains recorded and requires its own corrected-flow evidence.

## Result

An isolated Wllama-derived browser runtime loaded and generated with Liquid AI's pinned `LFM3-1.7B-QAD-Q4_0.gguf` on this PC. This proves that LFM3 architecture, tokenizer, chat template, QAD Q4_0 weights, and WebGPU execution can work together in that spike build. It is not a product-generation test, quality acceptance, or iPhone result.

## PC measurements

Environment: Windows x64, Chrome 156, 12 logical hardware threads, browser `deviceMemory=16` GiB, cross-origin isolated. WebGPU identified Intel `gen-12lp`; adapter name was unavailable. The adapter advertised `maxBufferSize=2 GiB` and `maxStorageBufferBindingSize=2 GiB` (rounded; exact API value was 2,147,483,644 bytes).

| Runtime / operation | Measured result |
| --- | --- |
| CPU-WASM model load | 28.99 s first load; 29.50 s after page reload in the first harness configuration |
| CPU-WASM generation | 23.86 s for 5 visible tokens; Japanese answer `準備ができました。` |
| WebGPU model load | 24.81 s first load; 13.49 s on a later OPFS-cached load |
| WebGPU generation | 5.04 s first short answer; 4.01 s on repeat; 5 visible tokens; same Japanese answer |
| Prompt accounting returned after generation | 40 prompt tokens, 5 completion tokens, 45 total |
| WebGPU placement from llama.cpp logs | output + 23 repeating layers; 25/25 layers offloaded; 993.13 MiB model buffer on WebGPU and 205.08 MiB on CPU |
| WebGPU context/cache at this run | `n_ctx=1024`; 12 MiB non-SWA KV, 10 MiB SWA KV and 2.44 MiB recurrent state on WebGPU; 63.21 MiB WebGPU compute buffer |

The short run suggests roughly 4.8× lower wall time for this five-token output with GPU offload than CPU-WASM. It is not a sustained tokens/second benchmark and does not predict phone thermals, long-context behavior, output quality, or memory headroom under other tabs/apps. LFM3's advertised 256K context was not tested; this run intentionally used 1,024 tokens.

The chat template was read from the GGUF. Its `enable_thinking` option materially affected the test: the default thinking path used a 64-token cap without producing visible answer text in 233 s; explicitly setting `chat_template_kwargs.enable_thinking=false` yielded the five-token answer in the timings above. This is a template/runtime setting to expose deliberately, not a universal instruction to disable reasoning.

An isolated Wllama v3 count-action patch then reused the same message/chat-template parsing path as generation. For one Japanese request, pre-generation count was 40 and post-generation `usage.prompt_tokens` was also 40. This establishes a viable exact-count implementation path for that fixture. It does not cover tools, JSON mode, multimodal input, long prompts, or template-option combinations, and the patch is not in product code. Pinned source revisions, patch hashes, and build artifact hashes are recorded in [research/runtime/wllama-lfm3](../research/runtime/wllama-lfm3/README.md).

## Cache observation

Weights were served from a local workspace HTTP server. The first server omitted `Content-Length`; that made the cache metadata invalid and caused later GETs. After fixing the test server to send the exact file length, the next model load reused the OPFS cache: only metadata `HEAD` requests appeared, with no model-file `GET`. This confirms one same-origin cached asset reuse path in this Chrome profile. It does not prove browser storage survival after eviction, PWA offline cold launch, runtime/WASM offline availability, or an Airplane Mode + force-closed restart.

## Compatibility workarounds and limits

Wllama 3.12.0 was pinned before the selected llama.cpp LFM3 commit and was not a direct compatible package pair. The isolated spike needed a local one-line `format_prompt_rerank()` call adjustment in `cpp/wllama-context.h`; the WASM build also hit an upstream `std::max` mixed-integer-type compile error in `deepseek41.cpp`, temporarily fixed only in the scratch copy. The runnable artifacts were generated under ignored `outputs/runtime-development/wllama-lfm3-spike`; no Wllama or model runtime source was added to the product. The two submodule untracked files that predated this spike were preserved.

Verified: CPU-WASM build; WebGPU-WASM build; GGUF hash; model architecture metadata; GGUF tokenizer/chat template; actual Japanese generation; WebGPU adapter selection and 25/25 layer placement; OPFS reuse with correct HTTP length; one pre-count/post-usage agreement (40/40). A later broader-prompt run stalled during model loading before those additional prompts ran; it is inconclusive and is not evidence that those prompts or the model are incompatible. Not verified in the spike: tool-call accuracy, JSON pre-count, Stop/cancellation, long-context preflight, sustained performance/thermal behavior, or comparative Japanese quality against Bonsai. Product-level generation, full offline PWA cold restart, Android, and iPhone/iOS are also unverified.

### Safari 26.6 compatibility target

The supplied iPhone run reported iOS 26.6.1 and `standalone: false`. WebKit's Safari 26.6 feature list does not include JSPI; WebKit's Safari 27 beta announcement says Safari 27 beta adds WebAssembly JSPI. Therefore the tested memory64 + JSPI spike is not an appropriate default for that reported Safari version. A no-memory64 Asyncify compatibility build is required for Safari 26.6 unless a capability probe on the actual browser proves otherwise. WebKit references: [Safari 26.6 features](https://webkit.org/blog/18178/webkit-features-for-safari-26-6/) and [Safari 27 beta](https://webkit.org/blog/17967/news-from-wwdc26-webkit-in-safari-27-beta/). This is a browser-feature inference, not a test on the reported iPhone; `standalone: false` also means that run does not verify an installed Home Screen PWA launch.

The Windows Asyncify + wasm32 compatibility artifact completed and passed `wasm-opt` validation with the build feature set. With JSPI deliberately hidden to exercise the compatibility route, the same GGUF loaded in 30.67 s on CPU and generated a five-token Japanese response in 27.04 s; the pre-count matched reported prompt usage (40/40). This proves a PC Chrome compatibility-route smoke test, not Safari or iPhone support. A compatibility build with 25/25 layers on this PC's Intel D3D12 WebGPU adapter lost the device (`DXGI_ERROR_DEVICE_HUNG`); this is a host/backend failure, not evidence of LFM3 architecture incompatibility. No Safari 26.6 GPU generation has been verified. A later 16-layer compatibility request in the same Chrome process also completed load and generation, but DevTools confirmed `requestAdapter()` returned null after the prior device loss; it therefore ran without WebGPU and is not partial-offload evidence. No repeated GPU retry was made in that degraded browser process. The compatibility configuration uses wasm32 and has a 4 GiB linear-memory ceiling, so actual memory/context fit must be assessed per device and cannot be inferred from the 1.05 GB GGUF size.

## Product model load note · PC Windows Chrome · 2026-10-28

The product's LFM3 Q4 load path previously performed a whole-file SHA-256 pass during normal load even though model preparation had already verified and stored the immutable GGUF in OPFS using the pinned SHA-256 as the filename. One Developer Performance report on build `50689e4fb62698a7` measured 23.33 s verification within a 32.3 s total load. The product now avoids repeating that pass only for the same in-memory `File` object read from the pinned digest-named OPFS entry after expected-size and digest-name checks. New/imported arbitrary files and explicit Prepare/Verify still receive full SHA-256 checks.

On updated build `cd32f2d76c1eb0b2`, one same-profile Windows Chrome 156 browser-tab Performance run measured verification 2.9 ms and total load 14.6 s. Runtime initialization took 14.55 s in this observation. First token was 4.90 s, overall generation 8.14 tokens/s and native decode 11.74 tokens/s for 56 input and 128 output tokens. Since runtime startup and generation varied from the preceding sample, report the verification reduction as the confirmed effect; treat the single total-load and generation values as observations, not stable performance claims. App connection mode was Offline, but the host browser remained online (`navigator.onLine:true`), and the page was not in standalone mode. No iPhone, thermal, memory-fit, quality, or Q4-vs-Q8 claim follows.
